# Single-source, state-selected self-improvement: revision 7 feasibility proposal, review pending

**Design only; no model, training or environment was run.** The two consumed DEV cases cannot supply an observed corrective label for the A loop: both products alternated look/examine for 50 steps and lost. B is a different task, succeeded for both products in 9 and 11 steps, and supplies no A-state counterfactual. The interrupted C candidate is UNKNOWN. ## New causal question

With the same initial P0, source policy, successful parent episodes, number of examples, per-pair supervised token ID sequences, training schedule and evaluation roster, does **selecting states following an observed repeated look/examine pattern** for self-imitation change downstream task success compared with selecting matched ordinary states from those *same* self-success episodes? A frozen P0 provides the no-update reference. This tests the effect of the training-state selection policy, not an online selector, runtime memory, a recovery operator, or DPO. Freeze the original agent prompt, parser, model product and inference settings. The fitted LoRA product is a separate candidate; baseline remains untouched.

SI-U1 asked self-success versus expert data across 78 training parents per arm; both tasks/states and source differed. Its 67/82 vs 65/82 and 68/82 outcome is inconclusive and does not isolate state selection. Here both treatment arms use the same P0 self-success episode per matched pair: the manipulated factor is which single already-recorded state from that episode contributes the target. Hindsight selection on successful episodes still excludes all failed trajectories and can cause selection bias; it is not evidence that an action caused later success. R19's 2/36 oracle gap is a separate recovery-duration observation, not evidence for this SFT treatment.

## Minimal prospective data artifact

Use only an already available, permitted pool with verifiable same-P0 product identity, complete successful original trajectory, exact raw public model input, action map, selected output token IDs and full native success receipt. Do not invent a missing prompt, action or terminal result. Before scanning, freeze the **exact ordered roster of at most 128 candidate training parents**, the exact first recorded episode identity for each parent independent of its outcome, eligibility and matching rules, and the independently fixed evaluation roster and relevant lineage boundaries. The actual candidate roster may be shorter than 128; 128 is an upper limit, not a claim that any eligible assets exist. Scan the fixed list in order and select the first 16 qualifying parents. For each candidate examine only its predetermined first episode and at most one pair; never switch episodes, change ordering, add parents or expand the pool. Stop scanning as soon as 16 qualify; mark every remaining candidate `NOT_SCANNED_AFTER_SELECTION`. If the entire fixed roster yields fewer than 16, stop feasibility and retain all rejections. A known nonqualifying result is rejected with a recorded reason; an inability to verify claimed identity, input bytes, required evidence or the scan ledger is a technical UNKNOWN and stops the scan rather than silently treating the problem as an ordinary negative. Do not inspect evaluation outcomes for selection.

Predefined ordered screening within this frozen candidate roster is permitted by this **proposed new protocol**, whereas post-result substitution, an unlisted candidate, another episode for a parent or an expanded pool is not. Preserve a ledger for every roster row: frozen identity/order and episode reference, accepted/rejected/technical UNKNOWN/unscanned state, applicable reason, input hashes and selection-code identity. Do not mark unscanned as failed. Screening only successful qualifying episodes induces selection bias; conclusions concern this highly selected corpus, not all P0 attempts or failed parents.

For intuition only, if the original 16-candidate rule independently had a 0.5 chance of qualification per candidate, the chance that all 16 qualify would be `(0.5)^16 ≈ 0.00153%`. This is an assumed illustration with independent identical probabilities, not an observed match rate, a scientific power calculation, or proof that a 128-parent roster exists or is sufficient.

For each episode construct a target/control pair only if:

1. Target's immediately preceding four recorded actions are exactly alternating `look`, `examine X`, `look`, `examine X` with the same X, and its recorded next action is an admissible non-look/non-examine action. This definition is intentionally narrow; the prospective project must settle exact string normalization in advance without editing raw history. It records an observed action after a loop, not proof the loop was broken or that the action was necessary.
2. Control is another non-loop state from the same successful episode with identical recorded next command **and Action-ID**; both prompts/outputs are the actual recorded strings/token IDs. In addition, their **entire loss-bearing supervised target token-ID sequences and full per-token loss-mask vectors must each be exactly identical**, in order, after the same frozen trainer transformation, including all loss-bearing special tokens. This strict no-padding rule also requires matching transformed example lengths; prompt token values and state content may differ. Equality of Action-ID, command, label length or group totals is insufficient; an unmatched pair is excluded, never relabeled. Lock tokenizer, target construction, loss mask, EOS handling and trainer before extraction, and verify the complete per-pair mask and loss-bearing IDs against recorded output and the actual transformation. Deterministically pick the lexicographically first (target index, control index) match. Controls are not automatically successful interventions at target states.
3. Each state has a known unique action mapping, a nonempty exact prompt whose hash matches the original receipt, a recorded valid action and token label, the episode's native final success, and source/task identifiers plus input, episode and product hashes. Do not replace missing information with model-generated labels; do not adjust labels or pad examples to force token matching.
4. Verify per-pair token-ID equality and group totals; match reported input-token count under a precommitted tolerance, e.g. at most 5% relative to the smaller total. Confirm each exact trainer-transformed input **plus** target and all automatically added special tokens fit the frozen trainer's actual total sequence length, with no truncation or packing. For the illustrative cap below the total is at most 4096, not 4096 input plus target. If the trainer's real limit or transformation is unknown, stop before training. If a predefined corpus of 16 parents does not meet these rules, **stop at feasibility**, disclose counts and costs; do not relax selection after viewing results or claim a training set exists.

**Decision- and parent-level dispositions:** Within the one predetermined episode, a decision may be skipped as a known nonmatch when reliable evidence establishes that it fails a frozen criterion, such as a non-loop history for the target or unequal recorded target IDs/masks for a proposed pair. Continue the already specified deterministic search within that same episode; do not treat a proven ordinary nonmatch as an infrastructure fault. Once sufficient trusted evidence establishes that the episode is a completed ordinary non-success or has no qualifying pair under the full frozen search, mark its parent `REJECT` with the specific reason and continue to the next parent already on the frozen roster.

If evidence needed to determine a decision's relevance, eligibility or match is missing, untrusted, conflicting, truncated or ambiguous, mark the affected decision and parent `UNKNOWN` and **stop the entire screening**. The same applies to missing or untrusted parent identity, episode identity, native completion, raw input, receipt, source/lineage or ledger evidence. Do not silently filter such a case as a known rejection, scan a replacement parent, or switch to another episode of the same parent to escape the uncertainty. The complete ledger must distinguish proven nonmatches and `REJECT` from technical `UNKNOWN`. A record provably irrelevant to a criterion need not have unrelated fields inspected, but irrelevance itself must be established from trusted evidence; do not infer it from missing data.

The two immutable JSONL files contain one original source decision per group for each of 16 distinct selected parents, with paired episode/decision identity, prompt and output hashes, Action-ID/command, loss-bearing target token IDs and complete loss-mask vectors, source product hash and completion receipt. Freeze a manifest with selection code hash, complete candidate ordering, full accepted/rejected/UNKNOWN/unscanned ledger, per-group parent and token totals, and disjoint evaluation parent hashes and lineage. As an engineering-only illustration, the retained `make_fake_pair.py` and `fictional_example.json` were made for the earlier design; they check fabricated matched, failed, mismatched-label/mask and overlength examples, but **do not implement or test this v6/v7 ordered candidate-pool rule**. They are not real training data and do not validate actual source assets or production SFT format.

### Outcome definitions and retained roster

The fixed evaluation estimand is success under the **prespecified H50 and parser policy**, with each episode classified separately:

| Recorded outcome | Protocol-defined episode success |
|---|---|
| A completed, internally consistent native environment terminal receipt says `won=true`; required source/identity, actions and evidence all verify, with no ambiguous truncation. | **1: success** |
| A consistent native terminal receipt says `won=false`. | **0: completed native failure** |
| The complete H50 policy budget is exhausted after 50 valid recorded environment actions, with no win and no environment truncation. | **0: completed horizon failure** |
| A complete, unambiguously ended model response fails the frozen parser's required action format or names an out-of-range action, and this protocol's predeclared rule terminates that arm as a policy failure with no fabricated environment step. Invalid output is not repaired or resampled. | **0: completed policy failure**, not a claim that the native environment itself terminated |
| Unstarted episode; interruption, process/device/identity/evidence or environment error; environment truncation; generation reaching a limit without a verified normal stopping condition; ambiguous or contradictory native win/terminal status; absent, inconsistent or untrusted action mapping; or an allegedly selected action that does not map to the actual legal action. | **UNKNOWN**, neither 0 nor 1 |

Model policy failure and technical failure are not interchangeable. UNKNOWN stops further execution under this proposal and stays in the planned roster; it is not filled, retried or replaced.

Native win/terminal and parser claims must come from the frozen accepted evaluation interface and be retained with the event record. Any unresolved distinction between a normal policy failure and an infrastructure or evidence failure remains UNKNOWN. These are prospective definitions for this candidate protocol, not retrospective reclassification of prior runs.

The primary observation is **protocol-defined episode success** per parent for the two state-selection arms, classified exactly as above; completed native, horizon and policy failures count as 0, while only unstarted, technically failed or indeterminate episodes are UNKNOWN. Use identical fixed seed labels to pair their products, then average each arm's three seed results within each parent and report paired differences across the **16 parent clusters**, alongside each fixed seed-pair result. The 48 parent×seed entries are correlated and are not 48 independent tasks. If all data complete, a 95% parent-cluster bootstrap interval may be reported descriptively (resample 16 parents, carrying all paired seeds together; fix replicates and bootstrap RNG seed before execution); tasks are nonrandom and intervals do not prove population benefit. Secondary outcomes: failure-only observed loop fraction with time-at-risk denominators, steps and input/output tokens; no claim of cause from a shorter successful trajectory. The comparison with P0 is descriptive and is not a confirmatory statistical test; its prespecified **+1/16** condition remains a necessary part of the prospective follow-up resource screen below. A genuinely independent follow-up needs independently sourced parents and a separately justified precision/power calculation. Unstarted or indeterminate results remain UNKNOWN in the full roster; no mean/interval implying a completed pair, imputation or automatic backfill. No automatic retry, best checkpoint selection or threshold change. Stop on source/hash/identity mismatch, budget breach, unknown physical work, incomplete paired evaluation or device conflict and retain raw receipts.

No actual data feasibility check, model/environment call, runtime readiness claim, experiment or promotion is made by this proposal. If the qualifying real pool or accepted execution chain is absent, the scientific result is **not yet testable**, and the fake artifact remains an interface example only.

Prospective feasibility decision, before any results: consider a separately designed and powered follow-up only if 16 training parents qualify within the frozen ordered candidate roster, every one of 112 evaluation outcomes is complete, budget/identity/evidence checks pass, the seed-averaged targeted-minus-control success difference is at least **1/16** (one parent-equivalent), and no more than two evaluation parents show control winning in a strict majority of the three paired seeds. Additionally, the targeted products' seed-averaged success must exceed the original fixed P0 by at least **1/16**, averaging the three targeted seeds within each parent before subtracting the one paired P0 outcome. Report, for each parent, the three targeted outcomes and P0 outcome, plus per-seed rescue/harm counts versus P0. If P0 succeeds on all 16 parents, this screen cannot pass; do not change the threshold or roster after seeing that result. The target-versus-control comparison concerns the selection intervention; P0 is a separate descriptive screen and cannot establish source or selection causality. This deliberately modest rule is a resource-screening threshold, **not** statistical significance, proof of improvement or a thesis-level conclusion. Report uncertainty even if it includes zero. Failure of a complete run to meet that screen means stop this fixed selection plan and document the outcome; UNKNOWN, interruption or incomplete data means no screen decision, no fill-in and no retry.
