# Local DAC isolation feasibility: synthetic-only real OS probe

**Result: DAC_SYNTHETIC_BOUNDARY_OBSERVED; NOT_INDEPENDENT_CUSTODY; NOT_REAL_RUN_READY.** We used existing `sudo -n` to run a no-network, no-model, no-environment Python child as existing `nobody`, with a parent-owned 0700 synthetic private directory, a separately traversable 0711 staging directory, one public 0444 fake input and one 0600 blocked fake input. The enclosing uniquely created temp path was traversable but not listable. `nobody` had UID/GID 65534, only its own group and zero effective capabilities in its own proc status. No account or system setting was created or changed.

The child read the exact allowlisted synthetic bytes. It was denied reading the sibling restricted file, listing the staging directory, reading or listing the private witness directory, and creating a file in the private directory. It wrote a fake result under a child-owned 0700 output directory with file mode 0600. While the child remained alive, the ordinary coordinator UID was denied access to that output, confirming that a real design needs an explicit reviewed output-ingestion path. The child deleted its file and exited 0; the coordinator removed the isolated temp tree. A private parent receipt records these 15 checks and cleanup. The private task record directory is 0700 and its receipt is 0600.

Two earlier *synthetic harness* attempts did not produce complete results: the first child emitted no report and its stderr was not retained, so its precise cause is not established; the second parent tried to stat inside the nobody-owned 0700 output directory and got PermissionError after the child finished. Both temporary trees were removed. After modifying the harness to obtain deletion status from the child, the third invocation produced the complete passing receipt. These were not retries of a scientific unit, and no scientific input or external model/environment call was made.

## Limits and practical next step

This verifies only the tested Unix discretionary access checks for the fabricated paths, current UID, group membership and capabilities. It does **not** prove that nobody can access *only* the staged input: it can access other world-readable paths and binaries, and inherited descriptors, environment, IPC, `[SYSTEM_PROCESS_PATH_REDACTED]`, network or library/kernel side channels require separate analysis. The parent can invoke sudo and root can bypass DAC; this is not an independent scientific custodian or evidence that the coordinator could not access a confirmatory set. The child's own report is not tamper-proof attestation. No CUDA device was opened or tested, and this probe proves no GPU ownership or runtime readiness.

As a minimum development-only design, a separate low-privilege actor process would receive a narrowly constructed public observation/action projection over a bounded authenticated channel; a distinct environment process would retain private PDDL and hidden state. Stage only the allowlisted inputs and runtime dependencies under reviewed permissions; clear environment and inherited descriptors; separately review world-readable files, helper binaries and network. Have a minimal trusted collector securely ingest the completed child output under controlled permissions, nofollow checks, size bounds and checksums, preserving failures and uncertainty. The current probe deliberately deletes its fake result; it is not that collector. A single Python process holding both PDDL and actor remains unisolated even under nobody. Build and independently test these interfaces with synthetic inputs before any real staging; preserve technical stops as UNKNOWN. Such a development boundary still cannot turn a coordinator-accessible dataset into independent held-out evidence.
