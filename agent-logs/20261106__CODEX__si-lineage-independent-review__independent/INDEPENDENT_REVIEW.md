## Results and limitations

1. **Template-graph closure passes the tested topology; ancestry closure is absent.** `lineage_validator.py:52–76` unions declared template edges and checks connected template components across partitions. An independent BFS comparison across all 64 undirected graphs on four fabricated template nodes, including bridges and cycles, agreed. The conservative transitivity of `possibly_related` can over-block and is described honestly by the author. In contrast, ancestry at `:72` is checked solely for equal strings; the schema has no parent-edge graph or complete ancestor sets. An independent synthetic example set a confirmation record's ancestry to the development record's identity and received `NO_DECLARED_CONFLICT`; making those two records point at each other still returns that status. The tool does not claim parent-pointer semantics; if callers interpret `ancestry` that way, both direct and cyclic relatedness are missed. Even with lineage-group labels, distinct labels representing shared ancestors can only be detected if an external authority establishes the mapping. A production isolation system would need explicit, validated ancestry semantics and appropriate closure/cycle checks, not infer them from this output.
2. **Declared completeness is an unauthenticated claim.** `:36–37,79–85` only checks whether `relation_inventory` says `complete_declared`; it cannot detect an omitted edge, undeclared parent, mislabeled canonical digest, or false origin. A `NO_DECLARED_CONFLICT` result always includes `independence_proven=false`, `custody_verified=false` and `claims_verified=false`; the meaning of exit 0 is solely no conflict *in supplied declarations*. Bridge nodes are deliberately accepted, but no independent node inventory can distinguish a valid bridge from an erroneously referenced identity. Truth, semantic canonicalization, overlapping lineages, support sealing and actual access control require separate real-world procedures and independent review.
3. **Coverage of partition presence is not enforced.** `:11,41–51,67–81` accepts an input containing just one fully declared development record as `NO_DECLARED_CONFLICT`; independent synthetic reproduction confirms this. Such a result is literally consistent with the submitted pairwise declarations, but does not establish that acquisition, feasibility, confirmation or their minimum supports exist. The actual proposed study has separate distinct-support and count requirements and must fail readiness when a required partition is absent. In particular, do not interpret exit 0 as the existence or readiness of four groups.
4. **JSON duplicate-key ambiguity is accepted.** `main()` uses ordinary `json.load` at `:88–91`, which retains the last duplicate key before `keys()` sees the mapping. A synthetic input with `classification` first set to `REAL` and then to `SYNTHETIC_ONLY` is accepted and exits 0. This is a concrete ambiguity in the stated malformed-input rejection rather than evidence that an actual protected task was processed. Any production successor should use a duplicate-key-rejecting parser before schema validation and independently bind the original bytes. Synthetic prefixes do not authenticate whether metadata are real.

The independent synthetic checks also verified missing ancestry/digest/template and `origin_status=unknown` give `UNKNOWN`, declared unknown relation inventory gives `UNKNOWN`, and representative boolean/list/integer values are rejected for identity/digest/partition fields. These checks do not validate all malformed inputs, actual identities, semantic independence or absence of exposure. No model or experiment was started.
