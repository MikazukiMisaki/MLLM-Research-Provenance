# Pair-owned production interface: static candidate, RESEARCH_HOLD

This directory adds a small non-executing adapter for independent review; it does not change any scientific or earlier candidate files. `static_adapter.py` provides code-byte checks, declaration-level product and manifest bindings, historical cost carry-forward arithmetic, and an in-memory draft matching the held fixed-product worker's argument/config keys. See `CONFIG_SCHEMA.md`, `source-addition.diff`, and `test-output.log`.

Two unittest cases in one process returned aggregate exit 0 (`test-output.exit`): exact v4 byte/hold inspection, explicit launch rejection, and fictional-record negative checks for empty plan, changed product identity, zero historical cost, materialization oversubscription, changed code/input/manifest hashes, and missing second-arm reset. No real task, actual product file, model, environment, GPU or real launch was accessed. The v4 source code alone was read for fingerprints and AST inspection.

## Exact limits of the connection

- The v4 held worker main is examined but never called or released. Its signature and held StageBudgetChannel are statically mapped; the actual parent scheduler remains a fictional-only scheduler and no code here launches or wires the production worker. Completing that integration requires a separately reviewed real production supervisor and retained HOLD; this is not a finished production adapter.
- Product identity is equality of supplied frozen record bytes and declarations. The digest's authority and actual adapter/base tree bytes were not independently verified. Code declaration hashes cover seven v4 candidate files, not every imported production dependency; filesystem path checks are lexical only and do not prove containment, no symlinks or protect against races. The actual worker checks differ and must be reviewed as a unit.
- `historical_used` and ledger SHA are unverified caller claims. Nonzero/ceiling arithmetic does not authenticate actual prior costs, establish a real budget, or replenish any spent materialization. New scientific permission must come from a valid future decision grounded in the actual ledger, not this draft. This adapter does not read or mutate any old ledger.
- Manifest and record JSON use standard `json.loads` and do not reject duplicate keys; a complete production validator must explicitly handle canonicalization/duplicate keys and bind exact on-disk bytes, all dependencies, product identity, fixed task manifest, and provenance under appropriate process and filesystem isolation. The schema and draft are not release-ready.
- Existing v4 process cleanup and UNKNOWN limitations remain. Actual end-to-end worker, runtime identity, GPU ownership, parent global accounting, real terminal outcomes, and time/device/token physical measurements remain unproved. Source fingerprint checks do not establish runtime imports or actor identity. No launch or scientific result is claimed.
