## Interface and fail-closed interpretation

1. **Exit code is narrower than readiness, as documented.** `sampler.py:210–226` returns 0 solely when the GPU parser labels the row OBSERVED. It does not require host memory, CPU or effective cgroup limits to be known, a resource threshold, or before/after sampler-source hashes to match. A new synthetic test patched GPU status OBSERVED, host/cgroup UNKNOWN and differing source hashes; snapshot exit was 0 and both differences were retained. This reproduces the documented contract, not a claim the saved actual snapshot drifted (its source hashes match). Any caller treating rc 0 or GPU OBSERVED alone as a complete monitor or safe launch would misclassify missing/drifted evidence. Require explicit per-field statuses, actual source/binary/input binding and freshness checks under a separately reviewed policy.
2. **Timeout/error evidence:** `:64–115` retains initial and repeated timeout partial stdout/stderr fragments independently, final output separately, observed direct-child return code and a conservative unknown descendant state; fake tests confirm repeated timeouts stay UNKNOWN rather than becoming a valid GPU row. A sample on nonzero return, timeout or malformed bytes is not marked OBSERVED. If kill, process I/O or a filesystem operation stalls, no finite wall-time guarantee is established; if final receipt writing fails or the process dies, no complete receipt is guaranteed. Do not infer zero resource effects from missing records.
3. **Device identity and capacity:** `:33–49` checks one row, A40 name, canonical UUID, numeric ranges and a one-MiB total-balance tolerance. It rejects an additional row even when the desired device is also present, which is conservative and may prevent use in multi-GPU environments. The expected UUID is not a proof the model's logical device maps to that physical GPU. Root ownership/non-writable file and binary hashing (`:52–55,74–76,103–108`) are useful provenance checks but do not remove the check-to-exec race or pin shared libraries, driver or kernel. Device-wide free memory is a changing observation, not an allocated reservation; others may allocate immediately afterwards.
4. **Cgroup and host status:** `:144–178` may emit an immediate visible v1/v2 literal but explicitly leaves ancestor effective limit and namespace mapping unknown/unverified. Its count field is recorded as literal bytes; the code does not establish effective headroom from it. `take_host_sample` (`:181–202`) can return GPU OBSERVED with host parse failures, unknown affinity or unknown cgroup. Do not use host available memory or a huge v1 literal as a verified per-process allocation limit; require an independently defined policy or treat it as unknown.
5. **Time and provenance:** `:215–221` records one monotonic start/end interval but no wall-clock, boot identifier, individual GPU/CPU read timestamps or independently authenticated clock. File mtime is mutable; comparing this record against a later process/reboot cannot establish a trustworthy age without a separately bound clock/boot context. Exact CPU sampling window and order within the interval cannot be independently reconstructed from per-read timestamps. Raw self-mount/cgroup metadata are locally retained and should not be published without separate review.

The code has no continuous supervisor, independent fail-stop, trusted process/descendant containment, global no-retry enforcement, model/adapter loading or scientific execution path. The above synthetic interface reproduction is a concrete integration hazard, while missing real monitoring, attribution and clocks are unimplemented limitations rather than observed real-world errors. Frozen implementation, budget, truthful UNKNOWN handling and a fresh resource check still require independent review before a bounded experiment.
