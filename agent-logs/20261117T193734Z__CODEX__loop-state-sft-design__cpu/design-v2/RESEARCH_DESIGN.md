## New causal question

With the same initial P0, source policy, successful parent episodes, number of examples, per-pair supervised token ID sequences, training schedule and evaluation roster, does **selecting states following an observed repeated look/examine pattern** for self-imitation change downstream task success compared with selecting matched ordinary states from those *same* self-success episodes? A frozen P0 provides the no-update reference. This tests the effect of the training-state selection policy, not an online selector, runtime memory, a recovery operator, or DPO. Freeze the original agent prompt, parser, model product and inference settings. The fitted LoRA product is a separate candidate; baseline remains untouched.

SI-U1 asked self-success versus expert data across 78 training parents per arm; both tasks/states and source differed. Its 67/82 vs 65/82 and 68/82 outcome is inconclusive and does not isolate state selection. Here both treatment arms use the same P0 self-success episode per matched pair: the manipulated factor is which single already-recorded state from that episode contributes the target. Hindsight selection on successful episodes still excludes all failed trajectories and can cause selection bias; it is not evidence that an action caused later success. R19's 2/36 oracle gap is a separate recovery-duration observation, not evidence for this SFT treatment.

## Minimal prospective data artifact

Use only an already available, permitted pool with verifiable same-P0 product identity, complete successful original trajectory, exact raw public model input, action map, selected output token IDs and full native success receipt. Do not invent a missing prompt, action or terminal result. Before inspecting outcomes, freeze exactly 16 candidate training-parent identities in a deterministic ordering from the permitted source roster and select the first preordered recorded episode of each parent regardless of outcome. At most one pair per parent: if that episode is failed, incomplete, unmatched or unknown, exclude it and never select another episode or parent to fill the gap. All 16 preselected parents must qualify; otherwise stop feasibility with the original denominator and explicit rejections. This is **not** a search for the first 16 successes from a larger pool. Fix ordering, definition of episode and matching rules before checking viability.

For each episode construct a target/control pair only if:

1. Target's immediately preceding four recorded actions are exactly alternating `look`, `examine X`, `look`, `examine X` with the same X, and its recorded next action is an admissible non-look/non-examine action. This definition is intentionally narrow; the prospective project must settle exact string normalization in advance without editing raw history. It records an observed action after a loop, not proof the loop was broken or that the action was necessary.
2. Control is another non-loop state from the same successful episode with identical recorded next command **and Action-ID**; both prompts/outputs are the actual recorded strings/token IDs. In addition, their **entire loss-bearing supervised target token-ID sequences and full per-token loss-mask vectors must each be exactly identical**, in order, after the same frozen trainer transformation, including all loss-bearing special tokens. This strict no-padding rule also requires matching transformed example lengths; prompt token values and state content may differ. Equality of Action-ID, command, label length or group totals is insufficient; an unmatched pair is excluded, never relabeled. Lock tokenizer, target construction, loss mask, EOS handling and trainer before extraction, and verify the complete per-pair mask and loss-bearing IDs against recorded output and the actual transformation. Deterministically pick the lexicographically first (target index, control index) match. Controls are not automatically successful interventions at target states.
3. Each state has a known unique action mapping, a nonempty exact prompt whose hash matches the original receipt, a recorded valid action and token label, the episode's native final success, and source/task identifiers plus input, episode and product hashes. Filter out truncated, unknown, ambiguous, duplicated or unverifiable examples; do not replace them by model-generated labels. Do not adjust labels or pad examples to force token matching.
4. Verify per-pair token-ID equality and group totals; match reported input-token count under a precommitted tolerance, e.g. at most 5% relative to the smaller total. Confirm each exact trainer-transformed input **plus** target and all automatically added special tokens fit the frozen trainer's actual total sequence length, with no truncation or packing. For the illustrative cap below the total is at most 4096, not 4096 input plus target. If the trainer's real limit or transformation is unknown, stop before training. If a predefined corpus of 16 parents does not meet these rules, **stop at feasibility**, disclose counts and costs; do not relax selection after viewing results or claim a training set exists.

The two immutable JSONL files contain one original source decision per group for each of 16 distinct parents, with paired episode/decision identity, prompt and output hashes, Action-ID/command, loss-bearing target token IDs and complete loss-mask vectors, source product hash and completion receipt. Freeze a manifest with selection code hash, ordering, reject counts/reasons, per-group parent and token totals, and disjoint evaluation parent hashes. ## Matched evaluation and finite planning envelope

Candidate plan, not a claim that inputs or a runnable evaluator exist: 16 training parent pairs, two state-selection arms × the same 3 prespecified paired training seeds **42, 43 and 44** from identical P0; 16 examples/arm, 4 epochs, microbatch 1, gradient accumulation 4 => 64 microbatches and 16 optimizer steps per run, **384 microbatches and 96 optimizer steps** over six runs. Equal optimizer/LoRA settings, source, ordered parent/example schedule, loss weighting, and identical per-pair target token sequences and full loss masks; a 4096-token total input-plus-target-plus-special-token ceiling and at most 16 target token IDs per example. Conservative independently counted maximums are 1,572,864 input and 6,144 target token IDs across all training microbatches; these ceilings must not be combined to permit sequences over 4096. No extra generation for sample acquisition is budgeted: source is existing successful episodes. If training context/labels cannot meet the fixed caps or source claim, stop.

Evaluate P0 plus the six frozen products on a prespecified set of 16 task parents disjoint from training parents and their known parent/template variants; record lineage as well as hashes, since unequal hashes alone cannot show independence. A shared task family is allowed but not itself proof of independence. Unknown lineage prevents an isolation claim and the claimed isolated evaluation; do not infer a new source or substitute tasks. Use the same tasks, environment seeds and ordering across products, do not select products or tasks after seeing results. Parent overlap/duplicates are forbidden. Previously used development tasks, if used, must be labelled exposed DEV and cannot support independent generalization; no assumption is made about an unverified task source. 112 episodes at H50: at most **5,600 generations, 5,600 environment steps and 112 resets** (5,712 env operations including resets), 112 environment constructions/initializations, 112 model loads and 112 task materializations as conservative process-level ceilings; generation input and output token ceilings are 22,937,600 and 89,600 IDs. Training adds six product-load attempts and optimizer work. Sampling, tokenization, data loading, validation and cleanup add I/O/CPU; **4 allocated device-hours and 6 wall-clock hours are proposed ceilings, not measured feasibility or a reservation**, including failures and cleanup; if this is inadequate stop, not extend opportunistically. Prior SI-U1, interrupted mainline and earlier alternative costs remain separate and must be added to a full project ledger, not zeroed.

The primary observation is native per-parent task success for the two state-selection arms; use identical fixed seed labels to pair their products, then average each arm's three seed results within each parent and report paired differences across the **16 parent clusters**, alongside each fixed seed-pair result. The 48 parent×seed entries are correlated and are not 48 independent tasks. If all data complete, a 95% parent-cluster bootstrap interval may be reported descriptively (resample 16 parents, carrying all paired seeds together; fix replicates and bootstrap RNG seed before execution); tasks are nonrandom and intervals do not prove population benefit. Secondary outcomes: failure-only observed loop fraction with time-at-risk denominators, steps and input/output tokens; no claim of cause from a shorter successful trajectory. P0 is descriptive baseline. A genuinely independent follow-up needs independently sourced parents and a separately justified precision/power calculation. Failed/unstarted/unknown results remain UNKNOWN in the full roster; no mean/interval implying a completed pair, imputation or automatic backfill. No automatic retry, best checkpoint selection or threshold change. Stop on source/hash/identity mismatch, budget breach, unknown physical work, incomplete paired evaluation or device conflict and retain raw receipts.
