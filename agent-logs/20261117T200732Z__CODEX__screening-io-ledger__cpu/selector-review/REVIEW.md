## Concrete partially failed read accounting

`select_pairs.py:32–39` checks a file's reported `st_size` against remaining byte limit **before** reading, but increments `bytes_read` only after the whole `f.read` returns. It does not durably or in-memory reserve that maximum as an outstanding debit before effect. In a fully fictional test I had the episode read return five bytes internally and then throw `OSError`. The selector emitted overall `status=UNKNOWN`, parent `UNKNOWN`, and stopped; however `counters.bytes_read` equaled the completed manifest length and did not include those five bytes. `full_scan_budget=UNKNOWN` remains present, and README acknowledges failure counts cannot establish physical I/O. The observation therefore proves undercounted completed-call counters and missing per-read reservation/explicit incomplete-read accounting, not an actual physical I/O cap breach.
