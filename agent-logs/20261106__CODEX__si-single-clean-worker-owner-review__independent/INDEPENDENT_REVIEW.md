## Findings

1. **BLOCKING — worker discards returned reset/step observation when validation fails.** In `worker.py:192–203`, the external call's RETURN event contains operation/index only. The result is handed back in memory. `worker.py:217–223` validates reset feedback, goal and facts before sending the OBS event. `worker.py:228–235` validates step identity, score/done and facts before OBS. Thus a completed physical return followed by malformed or mismatching results leaves only the return marker; the original feedback/state/score/done needed for audit is not durably recorded. `reproduce_fake.py` uses the candidate's fake factory and confirms: an identity mismatch has step RETURN 0, no OBS stage 1, and no retained return-state fields; wrong facts has step RETURN 1, no OBS stage 2, and no retained return-state fields. Both stop rather than produce a false success. Fix for any future candidate: immediately serialize and durably journal bounded raw/sanitized return facts and actual score/done/action identity **before** semantic checks, or preserve an explicit serialization-unavailable marker and resulting UNKNOWN where objects cannot be serialized. Do not mistake physical RETURN for a valid observation.
2. **BLOCKING — owner discards an OBS it rejects.** `owner.py:267–270` calls `protocol.accept(event)` before `journal.append`. When the owner receives an invalid OBS, validation raises before the event reaches the journal; the exception handler records at most a generic reason. Independent fake reproduction constructs a pending observation and sends one with invalid facts: `ValueError`, zero journal appends and zero ACK writes. This is fail-stop for progress but loses the rejected evidence. Before declaring the lifecycle fixed, journal the bounded, identity-bound received message or a clear serialization/truncation/unknown record before semantic validation; prevent invalid events from authorizing continuation. Maintain sequence validation and durable START-before-ACK. Evidence retention is different from accepting untrusted content as truth.
3. **BLOCKING against the proposed one-pipeline-per-case budget — four visible PDDL-to-SAS calls are on the normal source path.** `textworld/envs/pddl/pddl.py:61–62` constructs `PddlState` during `load`; `:110–111` constructs another during `reset`. Each `PddlState` invokes `fast_downward.pddl2sas` twice at `textworld/envs/pddl/logic/__init__.py:169–172`. Therefore one uninterrupted load+reset on this exact source path calls it **four times**; early failure can stop before four. The owner logs only load/reset and correctly labels translation process counts UNKNOWN (`owner.py:307–308`), while the draft four-case engineering budget contemplated at most one pipeline start per case. Reconcile the stage definitions and revise physical limits/observability before any release. Distinguish these four Python function calls from actual OS processes and deeper compiler/native work; they are not proof of four subprocesses or a runtime observation. Any internal work not observable remains UNKNOWN, not zero.

## Controls that do work within stated limits

- `owner.py:23–32,281–284` and `worker.py:16–25,255–256` disable real entrypoints before intended claims, child spawn, input access and engine construction. The no-CLI-enable boundary is real for unmodified source, not protection against a same-user source rewrite. The future supervisor requires caller-provided hashes (`owner.py:284–290`) and does not by itself independently authenticate them.
- On the candidate's real code path, `worker.invoke` sends START before `fn`; the worker waits for matching ACK; owner authorizes order then appends and fsyncs before ACK (`worker.py:47–58,192–203`, `owner.py:72–82,267–271`). This is based on declared selected facts only; true environment names, language, actions, state/feedback, terminal success and object compatibility remain untested. Tests are fake.

Existing source explicitly admits lack of aggregate tree accounting/cgroup, global disk quota, hard CPU/wall/cleanup guarantees, descendant ownership and possible setup/death races. The code imports some Python dependencies before source self-hash, caller supplies the expected hashes, and mutable filesystem/runtime bindings are not an independent trust boundary. These are already candidly documented in the candidate README; fake tests cannot upgrade them to proven enforcement.
