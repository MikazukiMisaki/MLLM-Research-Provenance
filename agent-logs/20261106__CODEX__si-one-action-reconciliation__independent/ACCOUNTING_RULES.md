# One-action probe: conservative accounting rules

Design only. These rules are not an implemented validator, a real cost observation or an execution release. The first synthetic accounting candidate has a documented counterexample on unrecognized records and must not be used as a cost oracle.

Separate three quantities for every external operation: **recorded started**, **recorded returned**, and **budget reserved/charged**. A started event can precede the actual external call, and a missing terminal event does not prove whether the call ran or completed. Reserve budget before each physical model load, generation or environment operation; record independently what actually returned. Never label an attempted or uncertain operation as zero-cost merely because a terminal event is missing.

* A trustworthy `generation started` without `generation returned`, or a failed generation after start, is a consumed, uncertain generation attempt. The one-action probe reserves one generation; do not retry it automatically. Actual output/tokens/device time may be unknown.
* A trustworthy `step started` without `step returned`, or an exception after step start, is a consumed, uncertain step. Preserve the input state and raw event files; do not rerun the action or infer its final state.
* A failure before a call may be assigned zero **recorded** calls only when independent process/control evidence establishes that execution stopped before the call boundary. A missing, malformed, unanchored or contradictory ledger alone is not that evidence. Model loading, tokenizer work, CUDA setup, environment construct/load/reset and native temporary files each have their own separate start/return/cost record.
* If logs are missing or malformed and no independent pre-call stop proof exists, the bounded one-call/one-step budget should be conservatively reserved for each operation that might have begun, while explicitly flagging actual physical work as **unknown**. The nominal cap is not proof that an unchecked or buggy program could not exceed it. If extra starts/returns are recorded, charge at least the observed count and mark a budget violation; unrecorded excess remains unbounded/unknown.
* A returned event without a start is invalid evidence, but its existence still prevents a zero-work conclusion. A valid event hash chain or matching raw-file hash proves only integrity relative to a trustworthy separately recorded anchor; neither proves that all external calls were emitted. A zero process exit without complete, anchored and mutually consistent records is not a completed probe.
* Record initial feedback, normalized task text, full/public action mapping, pre/post facts, actual prompt, chat-template hash, input and output token IDs and raw decoded output locally. Keep actor-visible data distinct from audit-only facts. Record independent parent/worker termination, selected device, device-wide samples and process-visible measurements with their limits. File writes, log copies and terminal-anchor publication can themselves fail and must be reported.

The existing v4 guard, v2 one-action core and v3 core-event journal are separate synthetic candidates. They do not provide the model-load ledger, unified process supervisor, global run-identity enforcement, external anchors, complete process cleanup, per-process GPU attribution or formal scientific endpoint. A future exact reviewed composition must define and test the complete event state machine across all components, including loss of any ledger and worker interruption.
