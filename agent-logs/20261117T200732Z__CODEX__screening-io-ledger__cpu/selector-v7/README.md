# Fixed-pool selector v7: synthetic-only, HOLD

New standalone CPU prototype under an explicit manifest SHA-256; no real task, model, GPU or environment was accessed. This is **not an approved or complete scan budget**, production source adapter, authenticated lineage, trainer integration, or permission to launch. Outputs retain `source_identity=UNKNOWN`, `execution_identity=UNKNOWN`, `lineage_authenticity=UNKNOWN`, `scientific_use=HOLD` and `full_scan_budget=UNKNOWN` even when fictional claims are selected.

Schema `SI_STATE_SELECTION_DEMO_V7` binds an exact manifest list of 1–128 ordered candidate parents and one declared episode each, as well as 16 declared evaluation parents. It prevalidates all candidate/evaluation parent IDs and declared lineage for disjointness before reading any episode. It scans in manifest order: known complete non-success or a fully verifiable episode with no matching pair is `REJECT`; malformed, missing, hash-drifted, conflicting or otherwise unverifiable required evidence is `UNKNOWN` and stops the scan. The first 16 `ACCEPT`s stop the scan; untouched rows are `NOT_SCANNED_AFTER_SELECTION`. On technical stop, later rows remain `NOT_SCANNED_AFTER_STOP`. Exhaustion before 16 yields `INSUFFICIENT`. No replacement episode, added parent or retrospective backfill is performed.

`ledger.jsonl` has one row per frozen parent and includes the episode ref/hash, disposition/reason and nested decision records actually examined. Well-formed loop/ordinary candidates and known nonmatches are distinct; a decision at which required validation fails is UNKNOWN. This conservative prototype validates all encountered decisions fully, even if a smarter implementation could prove an unrelated field unnecessary. Decision searches, action history, same-episode matching, exact target IDs and entire loss mask, full 4096 context bound, per-episode ID, decision ID, duplicate terminal/full-reference file-identity checks and train/eval **declared** lineage separation derive from the preceding synthetic selector. A known decision nonmatch is not a technical failure; pair search continues within the same episode. A missing trusted field is never silently classified as nonmatch.

Caller must supply positive `--max-files`, `--max-bytes`, and `--max-ledger-records` limits; the program accounts opened input files and successful userspace bytes read, and reserves one ledger record for each parent plus examined decision before examining it. Exceeding a limit produces UNKNOWN and stops. The pinned manifest itself counts as one read; outputs report counters and requested limits. If the parent roster itself exceeds the ledger-record cap or the manifest is unreadable/unverifiable, no complete parent ledger can be generated and `parent_roster_ledger_complete=false`. Counts following I/O failure cannot establish all physical I/O. Output-byte, CPU, wall and memory ceilings are **NOT_IMPLEMENTED** and source/lineage/physical execution authenticity is unproven. No numerical ceiling in tests is approved for a real scan.

`status.json` is the required authoritative status: `SELECTED_UNVERIFIED_CLAIMS`, `INSUFFICIENT`, or `UNKNOWN`; selection artifacts only arise in a fully qualifying cohort. Output-I/O errors or process death can leave partial files and no durable status; readers must treat those cases as UNKNOWN. Atomic/durable multi-file writes, bounded output bytes and same-UID concurrent modifications are unproved. Caller-declared source IDs can be forged and source files can be copied to new inodes, so duplicate checks are not source authentication. Terminal claims and action/label origin do not independently prove actual native success or generation. The provisional representation assumes a prompt-ID prefix plus label IDs, not an observed production trainer. These limits persist from v2 and must be independently resolved before any real data use.
