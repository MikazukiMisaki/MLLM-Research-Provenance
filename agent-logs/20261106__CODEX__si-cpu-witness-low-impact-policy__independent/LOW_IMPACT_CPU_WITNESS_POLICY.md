# Practical one-case CPU-only witness policy — proposed, not release

**Recommendation: a single self-authored, six-step engineering witness can be reasonable without a writable delegated cgroup**, provided the coordinator freezes a narrower explicit policy, obtains independent exact-byte review and verifies the direct process and evidence controls below. The previously proposed aggregate process-tree CPU/RSS/disk hard limits were an engineering proposal, not a user instruction; this policy does not pretend that cgroup-equivalent guarantees exist. It is a low-impact, stop-on-fault diagnostic, not a scientific sample, performance result, claim of task independence, or proof of zero impact on a shared server.

The user's standing authorization covers continuing this development work; do not ask them to repeat general approval. The internal exact-code review, observed fresh resources and concrete one-shot engineering release remain necessary to make this specific action reviewable. The current v2 owner/worker remains disabled and has unresolved independently reproduced snapshot-status/consistency issues; this document does not turn it into a runnable candidate.

## Observed local facts, not future admission

Read-only mount inspection in this session found cgroup v1 controllers mounted read-only inside the container; `/sys/fs/cgroup/memory` is not writable under `os.access`. Mount flags in `/proc/self/mountinfo` are read-only even where underlying superblock options report `rw`. A delegated per-run writable cgroup is therefore not established. Visible v1 memory limit was `9223372036854771712` and usage `34104332288` bytes at the sampled instant; do not equate the large limit with unlimited ancestor/host capacity. `/proc/meminfo` reported MemAvailable `126176824 kB`, and the evidence filesystem reported `35746292` KiB available. These are point-in-time shared-system values, not reservations or promises; ancestor policies, page cache and later use remain UNKNOWN.

A separately executed, owned **stdlib-only CPU child** set/read back CPU 2/3 s, address-space 128 MiB, per-file 1 MiB, core 0; `prctl(PR_SET_PDEATHSIG, SIGTERM)` returned success and initial parent matched. The parent opened that direct child's pidfd using the local x86_64 syscall, signaled it via `pidfd_send_signal`, and observed direct return code −15, with no model/ALFWorld/parser/GPU involved. Probe source SHA256 `498530f47e307f906411ad14c773ac67f7648ad19edca92d997e598ab93fa9d9`; raw stdout `a47e22f3d9029c65080166293e3ec8d37e9b16887367bdeaa687963316752bc9`, raw stderr empty and `cpu_probe.exit` contains 0. **This demonstrates only this test process and exact limits**. It did not kill the parent to test parent-death delivery, prove the pinned environment behaves identically, establish a hard process-tree quota, monitor unrelated workloads, or load the research runtime. `hasattr(os, 'pidfd_open')` was false in the current interpreter; using the tested syscall path is not proof that every Python/kernel/seccomp environment supports it.

## Scope, physical costs and timing

Select exactly **one** previously hashed self-authored development draft and its reviewed domain/grammar; one fresh process identity and one-shot claim, no model, GPU, recovery, learning, acquisition, evaluation or retries. The sole planned sequence is one direct engine construct, one load, one reset, at most six scripted step starts and one close. Count reset and step starts separately: ≤1 reset + ≤6 steps = **≤7 physical reset-plus-step starts**. Also journal construct/load/close starts, returns, failed/unknown operations, CPU/wall/disk and actual exit. A normal source path calls `pddl2sas` twice in load and twice again in reset, i.e. **four expected Python function calls**, not four proven OS subprocesses. If these calls are not separately observed, report them as source-expected with actual count UNKNOWN; do not claim either zero or exactly four actual calls. Any known nested/native/descendant work must not be double-counted as separate physical steps, and all unobserved work remains UNKNOWN.

This requires a narrow amendment to the original per-case five-step cap; 6 is not authorized by that cap itself. Count the attempt within the original ≤200 candidate-validation envelope if the coordinator freezes this accounting. Holding the remaining 199 one-reset-plus-five-step allocations fixed, the modeled validation ceiling becomes `199 × 6 + 7 = 1,201` reset-plus-step starts, **one more** than the earlier 1,200; under the earlier illustrative 8,540 total and otherwise unchanged assumptions it would be **8,541**. Those totals exclude prior historical cost, compilation/native work, any model loads/training, tokenization, process cleanup and all unknown tail costs. If the one-case attempt is outside the 200-attempt envelope, freeze an additional allowance and full total before start. Do not carry over the four-case 1,216 amendment as if it describes this single-case plan.

## Must be true before the single real attempt

1. **Exact, no-retry scope:** final worker/owner/return-evidence code and fixed argv/environment, public-domain and one problem/grammar byte hashes, action plan, caps and output directory are independently reviewed and pinned; source and input checks occur before start and match again on completion where feasible. The experimental mode is self-authored `DEVELOPMENT_ONLY`; no file or source path scans unrelated historical/protected tasks. One exclusive local claim and fresh output prevent ordinary same-path rerun; no retry or automatic next case. Same-user mutation/TOCTOU is not solved by hashes and is a disclosed trust boundary.
2. **Evidence before continuation:** direct owner writes and fsyncs a unique START before acknowledging each external construct/load/reset/step/close, and never calls the next operation on unacknowledged or corrupt state. Bounded returned observations/score/done/grounding are persisted *before* semantic acceptance, or explicit partial/unserializable UNKNOWN is persisted when possible; fail-stop on incorrect or incomplete critical data. Owner must retain rejected frames rather than validate-and-discard. Adjudicate the v2's reproducible `MISSING`/complete-status mismatch and raw-vs-observation consistency before treating those fields as evidence. Tests must cover refusal/failure of writes and ACKs as well as wrong instruction, ambiguous grounding, action result mismatch, missing goal conjunct and premature terminal. Lost fsync or torn storage cannot be made truthful by an invented completion.
3. **Direct-child identity and stop:** use a verified direct-child identity, such as retained pidfd acquired before GO, and a parent-liveness handshake; set and verify direct child PDEATHSIG or a reviewed equivalent before any engine side effect. A monotonic watchdog sends stop through the retained pidfd (TERM then KILL if needed) only to the owned direct child and records actual wait status. If identity, parent handshake or pidfd is unavailable before GO, stop before engine calls. If a kill/wait later fails, mark direct cleanup UNKNOWN and stop further cases. Never kill an unverified PID or unrelated GPU/user process. A separate owner/watchdog can die or block, so the wall timer is an enforceable best-effort operational bound, not an absolute bound on kernel activity or uninterruptible I/O.
4. **Direct limits and admission:** in the actual pinned child, set and read back a fixed per-process CPU limit (proposed 25 s soft/30 s hard), address-space limit (proposed 4 GiB), per-file limit (proposed 128 MiB), and core 0 before importing or constructing the engine; use a monotonic nominal ≤30 s for the child phase. These numbers must be reviewed against the exact candidate and any stricter existing host limit; the tiny probe's different settings do not establish feasibility. Note CPU includes inherited waited-child usage according to kernel behavior, AS is virtual address space not RSS, and per-file cap is not a total output cap. Freshly inspect available host/cgroup-view memory and evidence volume before launch, use a fresh local-only scratch directory, require a practical reserve (e.g. ≥2 GiB disk and ≥3 GiB host available memory unless a more conservative frozen value applies), bound journal message lengths, and monitor own scratch size with a predeclared stop threshold. Sampling is a soft guard with overshoot possible, not a hard filesystem quota. An unreadable resource value, insufficient reserve, failed verified direct limits, absent owner/watchdog, missing input, or an active conflicting owned run blocks GO. Load pressure and current server policy must also be checked without disturbing other jobs.
5. **CPU-only source and truthful status:** static review must confirm no model/tokenizer/weight, GPU/CUDA, training or agent-generation call on the chosen engine path; the child's environment must be fixed and logged. `CUDA_VISIBLE_DEVICES=''` alone is not proof of device denial. Child code may import PDDL/ALFWorld native components; their resource/initialization behavior is not exhausted by the prior tiny probe. On a fresh exact source and actual clean runtime, verify module origins where feasible and report partial dependencies rather than falsely certifying complete provenance. If the reviewed source calls a model or GPU, scope is violated and release must stop.

## What can honestly remain UNKNOWN for this limited witness

- A cgroup-enforced aggregate process-tree memory/CPU/disk ceiling; actual descendant/native/kernel-tail use or external impact not observable from a direct-child wait; process-group escapes; host activity by others; and exact total disk usage between soft samples. No claim of global process ownership, resource exclusivity, external atomicity or sandbox security is permitted. If observable evidence of runaway/escaped work, lost direct child, monitor failure, unbounded output or declining resources appears, terminate the owned child safely and mark cleanup UNKNOWN; do not launch anything else until adjudicated.
- Whether the case has ever appeared in another dataset/pretraining, whether similar goals generalize, and if a model would solve it; this is a self-authored debug witness and cannot support an independent test-sample claim. Direct-engine success does not establish the standard production wrapper without a separate comparison.
- Native translation internals and exact parser/engine memory use. Expected four PDDL-to-SAS function calls are a source-level estimate; no compile/translation outcome is assumed. A startup failure or timeout is a technical stop with its incurred cost, never a reason to silently increase limits or retry.

For an otherwise well-controlled one-shot diagnostic, **absence of a writable cgroup alone need not be a permanent blocker**, provided these residual unknowns and lack of strict tree-wide guarantees are accepted in the release and evidence report. Conversely, inability to identify/control the owned direct child before GO, verify the agreed direct limits, keep durable operation starts, preserve observable returns, enforce six-step/no-retry boundaries, or recognize actual errors/unknowns is a genuine prelaunch blocker. No technical stop or missing data may be counted as a valid failure/success or erased from the cost ledger.

This proposal does not grant release, fix candidate code or authorize a change to the frozen scientific protocol. Only a separate exact-code review and coordinator engineering decision may select it.
