## Concrete duplicate-source counterexample

`select_pairs.py:67–75,77–108` checks distinct parent strings and train/evaluation declared-lineage overlap, but does not reject two training parents' episodes that share the same claimed episode ID, identical referenced decisions and the same terminal reference. Using the supplied fully fictional fixture I changed parent 2's episode JSON to reuse parent 1's `episode_id`, `terminal_ref`, and all decision references while retaining its own parent string/lineage and updating the manifest hash. `build` accepted all 16 and returned two entries with identical target/control source refs and terminal, counted as different parents.

Independent reproduction: `reproduce_alias.py` SHA256 `534170676bf6f50d64bc1998bf8465daaa687fd976dc023728044dcfe5c63c07`; `reproduce_alias.log` SHA256 `36650ea4ee8c47532c7b8bc12f3ab468e5da16ef5d0898d4a06c482009f6ae1b`. This is an internally contradictory fictional claim, not an assertion that real data contain duplicates. It conflicts with the proposed requirement to filter duplicated/ambiguous source decisions before treating 16 parent pairs as distinct.

Define the scope of original parent/episode/decision IDs and their cross-parent uniqueness, then reject conflicting reuse of the same claimed source record/decision references and parent identities without replacement. Do not reject independently authenticated distinct episodes solely because their token content happens to coincide; episode IDs may be locally scoped and their scope must be explicit. Tests should include cross-parent alias, duplicate declared original decision identity, and valid independently sourced matching outputs. Such internal checks still cannot authenticate parent lineage or source bytes.

## What checks actually establish

- `read_file` uses explicitly referenced manifest hashes, per-file stable stat, no-follow on final component and size bounds; top manifest hash is caller supplied. This binds bytes to a caller's claims, not to an independently authenticated roster/product/physical run. Path race and complete chain authenticity remain unproved.
- Manifest contains exactly 16 claimed train parents with one episode reference each and 16 claimed evaluation parents; parent-string and supplied lineage-tag intersections across train/evaluation reject. It does not verify that the one episode is truly first, or that lineage tags are complete/authentic. No per-parent backfill is implemented; selection aborts if the provided episode fails. Claimed parent identity does not prove genuine distinct source parents.
- `select_pairs.py:83–108` reconstructs history from the supplied ordered action strings, requires the four-action loop, valid distinct action mappings, equal selected ID/command, exact target IDs and full mask, and caps provisional prompt + label sequence at 4096. It does not prove action log, history, prompt, action map or target IDs correspond to real model execution; the simplified prefix-plus-label mask format is not demonstrated to match the actual trainer. Matching token IDs does not authenticate their origin.
- `terminal` is simply a referenced JSON object `{complete, won}` and is not independently episode-bound or a native receipt. User-facing status remains `source_identity=UNKNOWN`, `execution_identity=UNKNOWN`, `lineage_authenticity=UNKNOWN`, `scientific_use=HOLD`; `SELECTED_UNVERIFIED_CLAIMS` means claim filtering, not established success. It would be clearer for machine consumers to expose terminal authenticity as UNKNOWN too.
- Output is a reference ledger after all 16 pass, not real SFT training JSONL. The manifest is required for resolving hash-bound references. Output I/O errors can leave partial files; readers must reject anything without fully validated successful status and independent completeness checks.
