# Four self-authored draft cases: model-free CPU witness budget (proposal)

**Status: DESIGN ONLY; no engine, model, GPU or task execution.** This proposes an engineering witness for four individually fixed, self-authored DEVELOPMENT_ONLY problem/grammar pairs. It is neither a scientific acquisition/evaluation nor proof of sample independence or generalization. The user's continuing project authorization permits the team to prepare and pursue this engineering work; this document is **not** an exact-code independent review, a concrete engineering release or proof that runtime checks have passed. Those gates remain to be completed by the coordinator before any process starts; do not ask the user again merely to repeat existing general authorization.

## Narrow purpose and input scope

After exact-source review and a separate coordinator engineering release, verify each reviewed draft against the approved *actual CPU engine adapter*: parse/compile/load, initial rendered task and unique groundings; execute its one predefined action sequence; and record each physical transition and final conjunction. Use the frozen production-relevant public domain/grammar and exactly the four existing PDDL and derived-grammar byte pairs listed in the original `capture_receipt.json` SHA256 `9eb18dc97e343c72a633a3ba99df5495b2327879004adeadfdccbad86f2fe59f`. Hence the physical reset-plus-action-step ceiling is **4 + 36 = 40 starts**, not 40 completed operations. A case that fails partway does not authorize spending its unused steps on another case. Include any actual separate construct, load, compile, translation, initialization and cleanup boundaries in the evidence and resource accounting; do not pretend they are action steps. For planning, expect **at most four compile/translation pipeline starts**, one per case, with at most one separately identifiable compile and one translation start *only where the actual implementation has those distinct external boundaries*. Establish actual API nesting before release. If compile/translation are the same external call or nested stages of one call, use linked ledger entries so a child stage is not double-counted as a second independent physical call; if the engine makes extra hidden calls or counts are unobservable, mark UNKNOWN rather than report zero. Any code path requiring an extra unbudgeted call stops before proceeding where possible; if it already started, preserve the actual cost and mark the scope overrun.

## Proposed resource ceilings and preconditions

These are conservative **candidate** hard limits requiring an independently reviewed runner/monitor that can actually enforce them; they are not a claim that those controls, resource headroom, or expected runtime currently exist. Establish exact enforceability and fresh values before release.

- Sequential execution only, one case process and its descendants at a time. Per case: **≤120 s wall time**, **≤120 aggregate CPU-seconds** for the case process tree, **≤2 GiB process-tree/cgroup peak memory** and **≤256 MiB incremental task-owned disk** including artifacts/logs. Overall: **≤480 s aggregate case time**, **≤480 aggregate case CPU-seconds**, **≤1 GiB incremental disk**. Allow a separate **≤120 s** for all supervisory startup, between-case audit and cleanup, producing a proposed **≤600 s total wall** from first launch to final exit. Wall includes compilation and translation; case clocks must not be reset by spawning descendants. Any larger useful limit requires a fresh engineering amendment before launch, not an automatic retry.
- Fresh read-only resource checks immediately before launch must show at least **3 GiB host available RAM**, **2.5 GiB effective cgroup memory headroom**, and **2 GiB usable free disk** on the evidence filesystem, with no more restrictive applicable quota; also check process/cgroup limits and host CPU pressure using the frozen admission rule. These are proposed thresholds, not observed conditions. Lack of a trustworthy value, changing cgroup, concurrent destructive filesystem pressure, missing hard-limit enforcement, or inability to save evidence means no launch. Do not assert disk quota or process-tree CPU hard enforcement from periodic samples: use reviewed cgroup, quota or equivalent; if no such enforcement exists, revise scope/controls instead of promising a cap sampling cannot guarantee.
- Set an empty CUDA device visibility in the approved clean environment and bind the reviewed CPU-only entrypoint. Require static and fake tests showing no model, tokenizer, adapter or CUDA load path; record the actual env allowlist and module origins without importing extra components. No generation, training, GPU initialization, preflight science, recovery branches or evaluation is included. A shared-GPU utilization sample is neither needed nor proof of CPU-only behavior.
- Use a fresh run identity per case, fresh exclusive output and one-shot claim, original and current input/code hashes, and an append-only ledger persisted before each external start and after each return/failure. Fixed reviewed argv, cwd and clean Python environment must match the approved launch record. Bind output limits before running and preserve all partial logs on failure. Per-case saved raw observations may contain only the explicitly permitted self-authored development case; no historical/protected task/trajectory/seed inputs.

## Immediate stop and cost disposition

On the **first** malformed/ambiguous command or instruction, initial goal mismatch, unexpected action/state/goal, invalid parse, precondition/grounding issue, nonzero/crashed/early or unobservable child, monitor loss, source drift, memory/CPU/disk/wall limit, missing or partial receipt, unsettled operation, engine failure, owner or descendant uncertainty, or evidence-write failure: stop the current run using only the reviewed process identity/ownership procedure, do not launch the remaining cases, and do not retry the failed case. Preserve raw bytes, claims, partially written outputs and timestamps; separately record why any descendant or internal kernel activity cannot be settled. Never kill unverified unrelated processes.

Ledger **starts, completions, explicit failures, and started-but-unknown** separately. An operation cut off after external start is not a zero-cost action or a model outcome. A not-yet-launched later case has zero observed starts but is **NOT_RUN**, not failed, valid or solved. If monitoring cannot prove cleanup or physical cost, mark process/operation/resource cost UNKNOWN and prevent onward execution; kernel/native I/O, translation internals, descendant resource usage and buffered writes that cannot be measured are UNKNOWN, not zero. Log actual versus planned budgets, any overrun, and the exact genuine process return code(s), not wrapper status substituted for child status.

## Relationship to the existing research budget

The prior scientific feasibility draft proposed up to 200 model-free validation attempts with **five** steps each. These 6/6/12/12-step cases cannot run under that per-attempt cap. This is a **proposed narrow amendment** to allow exactly these four single-attempt development witnesses, not permission for all future candidates to use 12 steps or exceed the overarching 200-attempt envelope. If counted inside that envelope, reserve four of the 200 attempts and charge all actual starts/compute; retain ≤196 remaining attempts under their separately frozen original rules. The old 1,200 reset-plus-step envelope was 200 × (1 reset + 5 steps); replacing four of those five-step allocations with these four exact 6/6/12/12 allocations gives a hypothetical revised ceiling of **196 × 6 + 40 = 1,216** reset-plus-step starts, **+16** versus 1,200, if all other 196 attempts remain under the old cap. This increase must be explicitly reflected in the total before release; it is not permission to exceed any existing whole-study cap silently. Under the earlier illustrative 8,540-operation subtotal, the same arithmetic yields **8,556** only if all other assumptions remain unchanged; training, model loads, tokenizer, compilation, failure tails, previously incurred costs and unknown native work are still separate. If not included within the 200 attempts, a new independent four-attempt allowance and total budget revision are required.

A later separate support-expansion proposal could require up to 30 steps per case and much more budget, but this four-case amendment does not approve or allocate that expansion. All numerical limits and outcomes above are prospective; no calls or resources were spent by this design.
