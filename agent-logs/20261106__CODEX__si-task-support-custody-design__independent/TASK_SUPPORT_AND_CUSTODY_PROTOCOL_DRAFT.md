# Minimal task-support and independent custody workflow

Status `DESIGN_ONLY_NOT_READY`: no task, trajectory or seed is generated, opened, listed or evaluated by this proposal. The only established self-authored PDDL case is a **development engineering case**. It cannot by itself supply the 20-draw pilot, the required separate supports, or independent confirmation. The definitions and steps below are implementable requirements for later review, not a claim that the present shared-account environment enforces them.

## Required roles and scoped access

**Coordinator/development team:** may inspect public domain/grammar, its own permitted development case and disclosed development/collection results; write and freeze a generator specification, validity code, canonicalization/version, common-pool and checkpoint recipe, 20-draw analysis, resource caps and runner. It may see only aggregated custody attestations described below for the unopened confirmatory support. It must not access the unopened support's task content, identity list, seed values, generation logs, raw validator messages or any interface that reveals membership. Feasibility identities/outcomes can be disclosed *after* the confirmatory support has been constructed and sealed, with any consequential changes triggering the re-freeze rule below. The coordinator must not read protected historical task contents to establish novelty.

**Custodian:** a person or separately administered process with an independent account/security boundary, restricted storage and audited access, who can invoke the frozen generator, validate task support and seal confirmation. The custodian must not assist development or checkpoint selection using feasibility/confirmation outcomes; they are responsible for generating and retaining fresh private randomness, mapping canonical/lineage identities, resolving task overlap and supplying only the fixed attestation. A simple second agent on the same account, repository or readable filesystem is **not** by itself an independent custody boundary; prior shared access and deletion cannot be disproved by a hash. If the actual tools cannot enforce separate credentials and storage, report `CUSTODY_UNVERIFIED_SHARED_ACCESS`, rather than simulating independent custody.

**Independent reviewer:** reviews generator/lineage code, frozen manifests, custody configuration, accounting and a fixed aggregate validation report before outcomes. The reviewer should not see private support or seeds either. Unless a trusted access-controlled audit mechanism actually exists, an auditor's self-asserted `sealed=true` is a claim, not proof.

The generator may be authored by the coordinator provided its code and any requested support definitions are frozen before confirmation is drawn. This minimizes the custodian's task. Independent task sampling/custody does not mean independent task families: conclusions remain limited to the declared generator and its two fixed families, not all ALFWorld or unseen natural-language variants.

## Executable sequence before model outcomes

1. **Freeze a development-only specification.** Version the public grammar and explicitly allowed domain assets; define two family templates, object constraints, action horizon, target mixture, target environment randomization distribution, canonicalization, structural ancestry rules, semantic-duplicate review, fixed validity predicates and maximum rejection attempts. Document how generated cases relate to the one permitted engineering case. Freeze the coordinator-visible generator code, validator and runtime by hashes before hidden support creation; a byte hash binds this version, not its quality or novelty. Avoid task or seed literals in the public specification. Do not treat a single development PDDL as a sample from the evaluation distribution.
2. **Implement and review a minimal lineage interface.** Each private record has a locally generated opaque identifier, partition, family, generator version, canonicalization version, canonical task digest, explicit provenance/derivation identifiers, validity status, a generation attempt number and a parent/ancestor set with declared relation type. Parent-edge graph closure and cycle detection must be implemented and separately tested on fabricated examples; missing fields/unknown parents are `UNKNOWN`, not a clean result. A template relation graph should conservatively flag shared, possibly related or transitively connected templates across partitions, with precisely documented overblocking. Validate input JSON with duplicate keys rejected and strict types. Check allowed family counts and required partitions explicitly; the current synthetic checker lacks all of these assurances and must not serve as the real custody gate.
3. **Construct permitted development/collection support.** Under the frozen attempt and resource caps, generate and validate a pool for acquisition/training. Development access and a permitted correction source do not automatically establish self-improvement: label each P0, human, planner or external-model contribution. Preserve accepted and rejected counts and reasons, without claiming their seed values or tasks were unseen. Deduplicate by exact canonical digest and generator ancestry; separately flag structural or semantic near-duplicates using the preregistered rule. Any unknown relationship is unresolved, not automatically different. Never inspect historical/protected material to search for prior exposure.
4. **Build feasibility and confirmation supports under custody.** Using independent declared sampling streams and the frozen validity checks, construct three non-overlapping lineage supports: development/acquisition, feasibility and confirmation. Candidate floor for planning: at least ten distinct verified canonical tasks per declared family in the feasibility support **and** at least ten per family in the independently sealed confirmation support. The floor does not prove representativeness, population coverage or statistical power. Count all invalid attempts and abort if a predeclared family-specific cap prevents forming the support. Validation must be treatment-independent; if rejection probability differs by family, define the **accepted-support** mixture rather than claiming the original generator mixture survived unchanged. No knowledge of model outcomes may determine support membership.
5. **Check overlaps without releasing a lookup oracle.** In the custodian boundary, compare the whole declared development/collection inventory and candidate supports using exact canonical identity, transitive ancestry closure, shared template connections, and predeclared structural/semantic checks. Perform a single comprehensive check on frozen sets; do not expose per-task lookup, unlimited membership queries, individual overlap identities, task contents or seeds to the coordinator. Export only fixed-schema counts/bucketed statuses needed for predeclared acceptance; suppress detailed small-cell information if it could disclose tasks. If equivalence or lineage cannot be established, seal as `UNKNOWN` and do not claim clean independence. Any actual overlap means `FAIL_OVERLAP` and requires regenerating the affected support within the prior attempt cap, without inspecting treatment outcomes; if a cap or frozen procedure is exhausted, stop and preserve attempted costs.
6. **Seal and attest.** The custodian privately draws task selection, environment randomization and arm-order randomness using distinct audited streams and freezes the complete manifest before evaluation. A manifest commitment should use authenticated, domain-separated keyed cryptographic commitments (e.g. HMAC of a canonical, versioned full manifest and per-run nonce using a securely custodied secret) rather than publishing bare low-entropy task or seed hashes that invite guessing. Public evidence contains a commitment, version hashes, role/account policy identifier, signed or otherwise independently anchored timestamp, aggregate counts per family/partition, validity and cross-partition audit status, and an explicit caveat on unverified historical/pretraining exposure. It contains no seed, task body, per-record identity or lookup response. Retain the secret and full manifest under custodian access control; disclose only for a legitimate audit after the protected stage and according to its prespecified policy. A commitment prevents undetected *post-commit changes* if correctly keyed, anchored and later opened; it does not prove the support or seeds were not previously seen, the original manifest was honest, or access controls operated.
7. **Freeze models and run bounded feasibility.** Bind P0 and separately produced C1/C4 final checkpoint bytes and their common training inputs/semantics, original and adapted runtime, decode parameters, study code, physical budgets and logs before evaluation. Execute the separate feasibility support first: predeclare ten draws per family, three arms each, selection with/without replacement, randomization and exact failure rules; retain 60 planned arm outcomes, identities and resource costs. A shared seed can pair initial randomness if runtime semantics support it, but is not proof that later RNG streams remain equal. Missing outcomes, unsupported lineage/custody, mapping or resource evidence yield `TECHNICALLY_INCOMPLETE`/`UNKNOWN`, not a completed sample. Feasibility outcomes are descriptive only. A 60-episode workflow PASS is not treatment efficacy or an authorization for confirmation.
8. **Keep confirmation protected or refresh it.** The outcome-blind checkpoint choice, analysis, accepted support distribution and target must be frozen before any confirmatory outcomes. If feasibility findings cause a change to the generator, validity/selection, target, outcomes, checkpoints, weighting or statistical decision, freeze the revision and generate a fresh independently sealed confirmatory support under the new version. Do not retrofit old support to the outcome or pool the feasibility sample as confirmation. If evidence shows unauthorized access or a lost commitment, mark the old support `COMPROMISED` and replace it under a fresh protocol; a new hash of the same exposed support does not restore independence.

## Interface: evidence, not an oracle

The following abstract fields define interfaces only; they are not sample tasks, identities or seed values:

```
support_submission = {schema_version, split, family, generator_version,
  canonicalizer_version, canonical_digest, derivation_ids, parent_ids,
  relation_inventory_status, origin_status, validity_status, attempt_index}
custody_attestation = {schema_version, protocol_digest, support_commitment,
  custody_method, custody_independent_status, access_audit_status,
  aggregate_counts_by_partition_and_family, validity_status,
  exact_overlap_status, ancestry_overlap_status, semantic_review_status,
  historical_exposure_status, pretraining_exposure_status, reviewer_status}
```

All status values must distinguish `PASS`, `FAIL`, `UNKNOWN` and, where applicable, `NOT_CHECKED`; never coerce absence to false or to PASS. Enforce an explicit field schema, unique keys, acyclic ancestry and referential integrity with known external roots, complete relation inventories or UNKNOWN, and a minimum support count per required family/partition. Duplicate record IDs, ambiguous canonicalization, missing provenance, unchecked derived ancestry or compromised custody cause `UNKNOWN`/`FAIL`, not implicit independence. Output only aggregate conflict existence/count under a strict disclosure policy, with an access-controlled sealed detailed log and a fixed upper limit on queries. A boolean collision check is itself an oracle if repeated on adaptive candidates. Bare digests of small or guessable tasks/seeds should not be published; HMAC/commitments and access controls reduce guessing but do not prove data nonexposure.

## What can be automated and what cannot

- **Automation can** check exact bytes and canonical digests against submitted lists, structural parent closure, cycles, declared template connectivity, schema/duplicate keys, counts, deterministic validity tests, disjoint set membership, fixed seeds' use without exposing their values, commitments against later openings, pinned source/runtime, bounded budgets and immutable append-only event consistency. Each conclusion is conditional on the completeness and honesty of inputs, correct implementation and an actually enforced security boundary. Do not assert an implementation exists merely because an interface is specified.
- **Automation cannot on its own** prove task semantic dissimilarity for arbitrary paraphrases, completeness of lineage or inventory, that someone never viewed an asset, unknown overlap with protected historical tasks or model pretraining, actual access controls from a text claim, representative task families, or successful treatment. Authentic institutional access logs and an independent custody boundary can support a limited nonaccess claim; their absence is `UNKNOWN`, not a default PASS. A model-scored similarity check would add model use and its own uncertain error and budget, so it must not be silently included.
- **If no independent custodian exists**, proceed only with an explicitly labeled exposed/development or shared-access feasibility study once its implementation, task permission, hardware and complete budgets are otherwise ready. Store auditable separation of generated sets and report what was visible, but label provenance `CUSTODY_UNVERIFIED_SHARED_ACCESS`, historical/pretraining exposure `UNKNOWN` and conclusions exploratory; no independently held-out or confirmatory claim is available from this shared boundary. Do not solicit or assume a new person is available, and do not let this procedural limitation block code/safety work that can honestly continue.

This protocol needs independent scientific and security review before use. It consumes no model, GPU, environment, tasks, trajectories or random seeds in drafting.
