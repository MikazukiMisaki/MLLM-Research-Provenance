# Single-source, state-selected self-improvement: falsifiable proposal

**Design only; no model, training or environment was run.** The two consumed DEV cases cannot supply an observed corrective label for the A loop: both products alternated look/examine for 50 steps and lost. B is a different task, succeeded for both products in 9 and 11 steps, and supplies no A-state counterfactual. The interrupted C candidate is UNKNOWN. No action from B is transferred to A, and a selected action is not presumed causal merely because its episode subsequently won. Existing data reviewed here do not establish that even one qualifying real training pair exists.

## New causal question

With the same initial P0, source policy, successful parent episodes, number of examples, supervised token labels, training schedule and evaluation roster, does **selecting states following an observed repeated look/examine pattern** for self-imitation change downstream task success compared with selecting matched ordinary states from those *same* self-success episodes? A frozen P0 provides the no-update reference. This tests the effect of the training-state selection policy, not an online selector, runtime memory, a recovery operator, or DPO. Freeze the original agent prompt, parser, model product and inference settings. The fitted LoRA product is a separate candidate; baseline remains untouched.

SI-U1 asked self-success versus expert data across 78 training parents per arm; both tasks/states and source differed. Its 67/82 vs 65/82 and 68/82 outcome is inconclusive and does not isolate state selection. Here both treatment arms use the same P0 self-success episode per matched pair: the manipulated factor is which single already-recorded state from that episode contributes the target. Hindsight selection on successful episodes still excludes all failed trajectories and can cause selection bias; it is not evidence that an action caused later success. R19's 2/36 oracle gap is a separate recovery-duration observation, not evidence for this SFT treatment.

## Minimal prospective data artifact

Use only an already available, permitted pool with verifiable same-P0 product identity, complete successful original trajectory, exact raw public model input, action map, selected output token IDs and full native success receipt. Do not invent a missing prompt, action or terminal result. For each preordered distinct training parent, select one preordered complete successful P0 episode before looking for a match. At most one pair per parent; if its first episode lacks a match, omit that parent and never switch episodes by outcome. Fix the ordering and rules before checking viability.

For each episode construct a target/control pair only if:

1. Target's immediately preceding four recorded actions are exactly alternating `look`, `examine X`, `look`, `examine X` with the same X, and its recorded next action is an admissible non-look/non-examine action. This definition is intentionally narrow; the prospective project must settle exact string normalization in advance without editing raw history. It records an observed action after a loop, not proof the loop was broken or that the action was necessary.
2. Control is another non-loop state from the same successful episode with the identical recorded next command **and the same Action-ID**; both prompts/outputs are each the actual recorded strings/token IDs. Deterministically pick the lexicographically first (target index, control index) match. Controls are not automatically successful interventions at target states; prompts, states and input token lengths can differ.
3. Each state has a known unique action mapping, a nonempty exact prompt whose hash matches the original receipt, a recorded valid action and token label, the episode's native final success, and source/task identifiers plus input, episode and product hashes. Filter out truncated, unknown, ambiguous, duplicated or unverifiable examples; do not replace them by model-generated labels. Do not adjust labels or pad examples to force token matching.
4. Match the group-level supervised token ID count exactly and match reported input-token count under a precommitted tolerance, e.g. at most 5% relative to the smaller total. If a predefined corpus of 16 parents does not meet these rules, **stop at feasibility**, disclose counts and costs; do not relax selection after viewing results or claim a training set exists.

The two immutable JSONL files contain one original source decision per group for each of 16 distinct parents, with paired episode/decision identity, prompt and output hashes, Action-ID/command, label token IDs, source product hash and completion receipt. Freeze a manifest with selection code hash, ordering, reject counts/reasons, per-group parent and token totals, and disjoint evaluation parent hashes. As an engineering-only illustration, `make_fake_pair.py` deterministically selects one matched pair from an explicitly invented success and excludes a fabricated failed episode. Its output `fictional_example_v2.json` is not real training data and does not validate any actual source asset or production SFT format.

## Matched evaluation and finite planning envelope

Candidate plan, not a claim that inputs or a runnable evaluator exist: 16 training parent pairs, two state-selection arms × 3 prespecified training seeds from identical P0; 16 examples/arm, 4 epochs, microbatch 1, gradient accumulation 4 => 64 microbatches and 16 optimizer steps per run, **384 microbatches and 96 optimizer steps** over six runs. Equal optimizer/LoRA settings, source, label counts and fixed 4096 input/16 target token per-example ceilings; max 1,572,864 input and 6,144 target token IDs across all training microbatches. No extra generation for sample acquisition is budgeted: source is existing successful episodes. If training context/labels cannot meet the fixed caps or source claim, stop.

Evaluate P0 plus the six frozen products on a prespecified set of 16 task parents disjoint from training parents. Use the same tasks, seeds and ordering across products, do not select products or tasks after seeing results. Parent overlap/duplicates are forbidden. Previously used development tasks, if used, must be labelled exposed DEV and cannot support independent generalization; no assumption is made about an unverified task source. 112 episodes at H50: at most **5,600 generations, 5,600 environment steps and 112 resets** (5,712 env operations including resets), 112 environment constructions/initializations, 112 model loads and 112 task materializations as conservative process-level ceilings; generation input and output token ceilings are 22,937,600 and 89,600 IDs. Training adds six product-load attempts and optimizer work. Sampling, tokenization, data loading, validation and cleanup add I/O/CPU; device time for all new work is capped at 4 allocated hours, wall time 6 hours, including failures and cleanup; if this is inadequate stop, not extend opportunistically. Prior SI-U1, interrupted mainline and earlier alternative costs remain separate and must be added to a full project ledger, not zeroed.

The primary observation is native per-parent task success for the two state-selection arms; average each arm's three seed results within parent then report the paired difference on all planned parents, and individual seed pairs. Report intervals as descriptive with 16 parents and 3 correlated seeds, not as proof of population benefit. Secondary outcomes: failure-only observed loop fraction with time-at-risk denominators, steps and input/output tokens; no claim of cause from a shorter successful trajectory. P0 is descriptive baseline. A genuinely independent follow-up needs independently sourced parents and a separately justified precision/power calculation. Failed/unstarted/unknown results remain UNKNOWN in the full roster, never success or failure; no automatic retry, post-hoc backfill, best checkpoint selection or threshold change. Stop on source/hash/identity mismatch, budget breach, unknown physical work, incomplete paired evaluation or device conflict and retain raw receipts.

No actual data feasibility check, model/environment call, runtime readiness claim, experiment or promotion is made by this proposal.
