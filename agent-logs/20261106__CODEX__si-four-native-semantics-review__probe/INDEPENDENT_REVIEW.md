## Domain semantics and required revisions

1. **Clean + deliver:** domain CleanObject (`alfred.pddl:399-417`) requires cleanable target, agent holding it, agent and SinkBasinType receptacle co-located, and adds `isClean`. PutObject (`:300-320`) additionally needs a held object, agent/destination location, accessible (not openable or opened) receptacle, object type, receptacle type and `canContain`. If acquisition is needed, PickupObject (`:184-208`) requires pickupable, target in the source, the actor at the source, source access and empty hand. The domain does not explicitly require water or an external light source for CleanObject. These are symbolic conditions, not proof of a realistically rendered or executable game.
2. **Heat + deliver:** HeatObject (`:419-436`) requires heatable held target, agent and MicrowaveType receptacle co-located, adds `isHot` and deletes `isCool`. It has no displayed door-open or powered-on condition, though other acquisition/delivery steps have their own accessibility preconditions. Do not infer that an installed wrapper or rendered command is behaviorally equivalent.
3. **Toggle:** ToggleObject (`:458-475`) requires toggleable target, agent at location, a receptacle at that location and target in that receptacle. It adds `isToggled` and conditionally flips `isOn`. It does not require holding the target or a separate light source. `isToggled(target)` and `isOn(target)` are different goals: if initially on, a toggle can leave it off while satisfying `isToggled`. **Revision required:** either describe this goal as a toggle/use action without claiming final on-state, or version a goal requiring `isOn` and state the relevant initial condition. The public grammar (`alfred.twl2:245-265`) supplies `use {o}` but its feedback branch tests `isToggled`, not `isOn`; do not use its “turn on” wording as independent proof of final switch state without real feedback-timing/state verification.
4. **Slice:** SliceObject (`:478-495`) requires sliceable target at agent's location and `holds(agent,tool)` with tool objectType KnifeType or ButterKnifeType; it adds `isSliced`. The proposal's separate target/tool is a sensible **additional design constraint**, not a `target != tool` precondition in the domain. If the tool is acquired via PickupObject, the tool must be pickupable and in an accessible source, the hand empty, etc. The domain's slice action tests `objectAtLocation` rather than a separate open-receptacle test, and has no light requirement. It does not promise a real knife, a target or correctly named unique commands exist; their availability and reachability remain UNKNOWN.
