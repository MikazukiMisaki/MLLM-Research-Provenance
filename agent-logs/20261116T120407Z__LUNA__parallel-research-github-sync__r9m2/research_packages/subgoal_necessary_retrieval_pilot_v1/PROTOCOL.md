# 必要取回反例：虚构题面开发试验 V1

**状态：开发性试验方案；结果出现后不得回写假设或更换主要统计。** 子目标交接是并行分支，不替代 self-imitation 主线。此前八题都把取回第一件设为错误动作，因此无法排除“永远避免取回第一件”这一简单规则。本试验询问：在需要取回第一件进行必要清洗的人工情境中，固定第二阶段能否选择取回第一件；在同一题面中，只改变给定子目标，选择是否随之改变？

## 设计

固定 8 个虚构情境：普通取第二件 4 个，以及两件都已放好但第一件脏、需取回清洗 4 个。每种结构仅有一套语义模板和 4 个词汇变体，不是 8 个独立任务、也不是新结构的确认集。每个情境固定目标、观察、空 inventory、诊断、4 个动作与编号；只在“目标相容的子目标”和“与目标不相容的子目标”之间切换。必要取回情境中的相容动作是拿出脏的第一件，不相容动作是拿出已清洁的第二件；普通情境则相反。这里的“不相容”仅按题面给定状态和即时任务进度判定，取走已放好的物体可能随后被纠正，不能把它说成逻辑上不可能完成任务或真实环境中不可逆的失败。四个候选还包括 `look` 和 `inventory`。正确动作编号每个结构中 A000—A003 各出现一次。

具体文字、动作映射和预期动作保存在 `cases.json`。这是事先人工判断的即时选择，不是环境产生的合法动作或完成状态的验证。第二阶段沿用现有研究中明确要求执行给定子目标的裸编号输出契约；没有增加检查器、selector、第二次恢复或新环境。顺序按情境固定，奇数情境先相容后冲突，偶数情境顺序相反；最多 16 次贪心生成，每次上限 16 新 token。每对其他提示字节必须相同。模型为本地原 Qwen3-8B、BF16、thinking 关闭；设备与配置需在运行时按共享资源协议确认。旧八题和本试验均为开发，不将其视为 held-out。

## 预先指定的结果

- 分开列两类情境各 4 个基础情境、两种子目标条件的选择：目标相容动作、冲突动作、其他合法动作、格式无效或截断、未运行。正确率一律同时报告分子和计划分母。
- 对必要取回四个情境，报告相容条件下实际选择取回第一件的数量，并对每个情境报告与冲突条件的动作是否变化。普通情境同样列报，供方向比较；由于结构同时改变了其他字段，结构间差异不能归因于“是否需要取回”的单一因果效果。
- 选择与子目标一致是动作层面的指令跟随，不是执行、环境进展或终局成功；不做统计显著性推断。固定执行提示本就要求执行所给子目标；相容条件动作正确不证明模型能主动发现错误子目标。
- 逐调用记录实际渲染提示、输入 token IDs、其 SHA-256、输出 token IDs、参数、编号映射、耗时和缺失／失败。摘要由实际调用输入计算，不为历史评分补造绑定。模型权重和机器路径不写入发布材料；本地记录不能独立认证物理设备或权重。

## 停止与资源

使用新的独立一次性输出目录，计划不自动重试；停止时保留所有已完成、错误与未运行项。逐个生成前后记账，输入超限、未确认终止符、GPU 状态不可核对、加载前利用率达到 5%、离散显存样本达到 43,008 MiB、设备身份不一致或日志失败即停止。利用率还会在其他采样点记录，但推理期间模型自身会贡献该值，不将它单独作为事后独占证明。采用项目现有共享 GPU 协调，优先保障主线，只有资源负责人确认时才调用模型；无条件放宽。本方案仅计划 16 调用以内的开发研究，不改变先前已耗尽的一次 120 状态重跑例外。没有模型运行时不声称已产生实验结果。
