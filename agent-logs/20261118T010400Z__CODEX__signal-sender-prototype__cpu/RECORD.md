# Standalone signal-info observer: synthetic CPU prototype

A single controlled test used only an owned receiver and that receiver's owned fictional Python worker. The receiver blocked SIGTERM in its initial thread and used a bounded `sigtimedwait` thread to collect raw `si_signo`, `si_code`, `si_pid` and `si_uid`. It created the direct worker with `os.posix_spawn(..., setsigmask=old_mask, setsigdef=(SIGTERM,))`, restoring the original mask and default TERM disposition in the child as part of spawn. The test inspected the live worker's `/proc/.../status` before signaling and observed SIGTERM not blocked. A known parent sent SIGTERM to its own receiver. The receiver recorded `si_code=0` (Linux SI_USER), the expected parent PID/UID, sent SIGTERM only to its own unreaped direct worker and reaped it with returncode -15. The waiter stopped, the receiver restored its prior signal mask and returned 0. Exact inputs and raw output are adjacent; no model, GPU, environment or real experiment was invoked.

This is a prototype, not a safe drop-in supervisor. The synthetic contract requires entry before any native or Python worker threads exist, SIGCHLD at default, and no external child reaper; checking Python's `threading.active_count()` alone cannot establish absence of native threads or external reapers. POSIX spawn failure before returning a handle, runtime death, SIGKILL, a worker that will not exit, late/pending signals around teardown, signal coalescing, filesystem failures, and untracked descendants remain UNKNOWN. The implementation retains an un-reaped direct-child PID on timeout but does not establish later cleanup; it has no durable journal or resource monitor. `si_pid`/`si_uid` are receiver-namespace observations, may be unavailable or refer to recycled/exited processes, and do not establish the originator's motivation. SI_USER, SI_QUEUE, SI_TKILL and SI_KERNEL distinguish delivery mechanisms, not the controlling person or system. The older training runs did not record siginfo, so their senders remain UNKNOWN.

Before real integration, independently audit signal disposition and process ownership for the actual runtime; arrange early process-wide masking without interfering with existing library threads; validate every spawn path's mask/disposition, robust waiter shutdown and stop behavior; preserve durable authenticated signal and supervisor receipts; handle signals at all transition boundaries and test explicit unknowns; demonstrate limits on descendants, timeout and restart policy. This material is not a release and must not be used to resume training.

## Existing launcher and supervisor integration conflicts

The existing weighted path uses `subprocess.Popen(..., start_new_session=True)` and relies on the returned Popen handle, identity capture, wait/poll and the outer monitor's single `wait4` reaper. Python's `Popen` interface here does not expose the `posix_spawn` signal-mask argument; merely inserting the observer and keeping Popen can cause a child to inherit a blocked SIGTERM. Running `preexec_fn` in a multithreaded Python process introduces a separate deadlock hazard and is not established safe. `os.posix_spawn` has a `setsid` parameter on this runtime, but this prototype did not exercise it, file descriptor redirection, `start_new_session` equivalence, process groups or descendants. It returns a PID, not a Popen object, so existing monitor APIs and identity/timeout paths cannot simply consume it. Exactly one designated reaper must own each child: do not run Popen.wait/poll and a separate waitpid/wait4 reaper concurrently, and do not signal a PID after it can be reaped/reused.

The current flag-only signal handler also cannot independently receive the same signal while that signal is blocked for sigwait; ownership and shutdown ordering would need redesign, including the interval before the wait thread starts and after it stops. The minimal program's output is not durable and its exception handling does not provide the launcher's authentic outer and inner failure receipts. A production integration must specify who owns spawn, stdout/stderr, immutable identity, pidfd or equivalent, exit/reaping, bounded cleanup, signal metadata and atomic interrupted/UNKNOWN receipts, and must demonstrate behavior when any step fails before acquiring a PID/handle. Pending signals at mask restoration can terminate the observer; preserve a fail-closed external record. Until all of that is designed and independently tested, there is no safe production integration claim.
