# Clean-family generator: development-only design

Status: DESIGN_ONLY; no new task, seed, environment call, model call or evaluation. A single self-authored clean case is available for a separate CPU witness, whose raw audit is pending. Even an audited success for that case would validate only that particular input and path; it cannot establish validity of this proposed family, its population size, or research performance.

## Objective and scope

Propose an auditable constructor for `isClean(object)` in the existing pinned ALFWorld domain. It shares abstract PDDL object types and operators with the independently authored transport family; it must not derive individual clean tasks from transport instances, protected tasks, model trajectories, results or task text. Public domain/grammar and a fresh self-authored, versioned rule specification are permissible common sources. The existing development witness is an implementation reference, not a template whose identifiers can be renamed to fabricate many independent examples. All outputs of this proposal, including any later pilot or invalid instance, are DEVELOPMENT_ONLY and permanently excluded from confirmation use. A separate design, budget and review would be required before any confirmation asset is constructed.

## Small, enumerable v0 population

Start with exactly one actor, one cleanable pickupable object, a source receptacle, a sink receptacle of required `SinkBasinType`, and two distinct locations. Each typed object and location has one unambiguous role; no decoys, extra goals, hidden inventory, equipment, stochastic transition, or new operator. The two allowed structural factors are:

1. Source `opened` initially false vs true; source is always `openable`. If false, the expected trace includes `OpenObject`; if true, the trace omits it. Actor initially holds nothing, object starts in source, goal is initially false.
2. Actor initially at source vs sink. When at sink, the expected trace first navigates to source; source and sink must occupy different locations. In either case the trace must reach source, pick up the intended object, navigate to sink, and invoke `CleanObject`.

This defines at most **four** structurally distinct role-based configurations, with expected traces of 3–5 scripted environment steps. A configuration is a hypothesis until statically validated and actually witnessed; four is an upper bound before feasibility and overlap exclusions, not four verified tasks or an effective sample size. Domain PDDL cost and real operation cost must be separately logged. The four variants do not, by themselves, support a well-powered self-improvement experiment. No RNG, selected seeds, candidate enumeration or task creation is authorized by this design.

Object, receptacle and location display names can be chosen from a finite self-authored, non-sensitive development vocabulary after checking the pinned grammar, parser rules and command output. Renaming identifiers, changing problem ID, or paraphrasing the instruction while keeping the same typed state/goal graph does not create a new structural case. Prompt paraphrase is not an uncontrolled diversity factor: pin one truthful goal template per grammar version. Do not assert any public ALFWorld arbitrary name is physically valid or has been runtime tested. A future parameterization beyond these two factors, including extra distractors, object categories, layouts and paraphrases, needs an explicit expansion and independent review.

## Validity contract

A generator candidate should pin public domain/grammar, its own source, parameter schema and canonicalization version; output a new exclusive DEVELOPMENT_ONLY directory; log exact input/output bytes, derived grammar diff, provenance and expected action types; never change baseline/public inputs. Static checker must reject:

- invalid or duplicate typed identifiers, unsafe grammar text or ambiguous rendered labels; source and sink aliasing; actor/object not placed exactly once; conflicting or duplicate facts; unsupported predicates or PDDL forms;
- incorrect domain/type bindings, missing `pickupable`, `cleanable` or required sink type; false or contradictory action preconditions; initially satisfied goal; inconsistent closed-world interpretation; wrong first-action expectation;
- any unknown public-domain action effects, unknown expression, unsupported grammar substitution, missing declared runtime dependency, source hash drift, or a predicted trace that does not reach the single intended goal using the pinned operators;
- unclear ownership/provenance, use of historical or protected task/trajectory content as source, exact duplicate or disallowed near-duplicate, or unknown split/isolation evidence when the candidate is being proposed outside explicitly isolated development.

Use an independently reviewed symbolic checker to replay each prescribed trace with type/precondition/effect assertions; it is a bounded static check, not a replacement for the real parser. The candidate parser and checker must have fake negative tests, including wrong type, initially clean object, ambiguous command, missing sink precondition, mapping drift and early terminal. No software test fixture or synthetic trajectory may be labeled as an actual engine witness.

## Deduplication and provenance without protected-content exposure

Canonicalize the typed object/fact/goal graph under role-preserving alpha-renaming, strip cosmetic identifier and problem-ID differences, and include initial actor/source states and every effect-relevant fact. Compute exact canonical hashes. Additionally record a versioned prefix graph/signature for the common open/pickup/navigation sequence, operator multiset/ordered sequence, role-relabeled initial state, target predicate and generation lineage. Exact goal-aware graph identity identifies direct duplicates; common prefix and role graph can flag cross-family near duplicates even where the goal differs. Text-normalized exact hashes are supplemental, not proof against paraphrase or semantic overlap.

Maintain a development lineage ledger independent of outcomes, with constructor source hashes and all accepted and rejected candidates. A candidate must not be generated by editing, cloning, paraphrasing or completing a specific transport task; shared symbolic operators and abstract roles are allowed. As a conservative initial rule, any clean and transport candidate with the same role-canonical initial setup and common action-prefix signature belongs to the **same leakage group**, even if goal predicates differ. Never distribute a group across development and a future assessment partition. Two variants may be retained inside development for debugging or paired mechanism work but are not independent tasks for inference. Structural group counts, not names or nominal task counts, bound effective novelty.

Do not access restricted historical/held-out task contents merely to perform this design. Ordinary hashes establish only exact byte equality: hash mismatch does not establish semantic independence. If a trusted custodian can later run a separately approved, privacy-preserving comparison over an authorized reference index, require a versioned method, scope, negative/positive controls and a signed aggregate or per-candidate pass/fail/unknown receipt; no false-negative rate or full coverage is presumed. Without a reliable comparison and provenance inventory, protected-set relationship remains UNKNOWN and candidates cannot be claimed independent or admitted to a confirmatory set. If index/custodian is unavailable, continue only isolated development; do not redefine UNKNOWN as PASS.

## Audit interface and decisions

For every later generated candidate, record in append-only order: source and schema hashes; creation identity/time; complete self-authored provenance statement; parameter values; raw and canonical task/grammar hashes; versioned canonical/prefix signatures; initial/goal invariants; static trace and independent checker result; dedup index version and match/unknown reason; group ID and permanent DEVELOPMENT_ONLY assignment; each validation attempt and its physical ledger; exact raw event/receipt hashes, exit code, stop reason and final disposition. Failed attempts remain present, not silently replaced. Output full task contents only within approved development boundaries; reports may expose aggregate counts, hashes and pseudonymous identifiers.

State transitions: DRAFT -> STATIC_REJECTED or STATIC_PASS -> WITNESS_PENDING -> WITNESSED_PASS or WITNESSED_FAIL/INCOMPLETE. A single case cannot be passed by a synthetic test; runtime mismatch, timeout, crash, missing/corrupt events, unexpected operation, changed pinned input, incomplete physical operation, or unverified final `isClean` means FAIL/INCOMPLETE. No automatic retries; a separate written adjudication must preserve prior costs and distinguish engineering diagnostics from a fresh scientific attempt. WITNESSED_PASS is a per-case reachability observation only, not a family or statistical certification. All escalation and access decisions remain with the project coordinator.

## Proposed per-case validation budget (not release)

Only after generator and each exact candidate are independently reviewed, allow **at most one** separate CPU-only witness per candidate: <=1 engine construct, <=1 load, <=1 reset, and <=5 scripted environment steps (actual variant may require 3, 4 or 5). No model invocation, CUDA, recovery, training, learned policy or statistical report. Each call journals started/returned/failed, raw observations and relevant state, selected exact grounding, per-step expected preconditions/effects, final goal, and real child exit. Unknown native internal work, failed/open operations, wall/CPU/RAM and all costs must remain explicit. Stop immediately on grounding mismatch, unexpected observation, resource/timeout failure or corruption, with no retry; never count a started failed reset or step as zero physical cost. Set an independently reviewed wall/CPU/RAM/file cap using the frozen runner's proven support and resource context; static script cost, PDDL cost and observed environment steps are different quantities.

A full initial four-configuration ceiling, if later approved, is 4 constructs + 4 loads + 4 resets + 20 attempted steps at most, with an individual fresh run identity per candidate; preflight and any diagnostic operations must be added separately, and no budget is consumed or reserved by this document. The actual total may be lower due to rejection, deduplication, or early stop. Source CPU witness already performed independently must be counted separately; this design does not authorize or trigger another run. Even all four passes do not establish sufficient data or permit scientific efficacy claims.
