# Multi-scene support construction specification — design only

**Status: DESIGN FOR IMPLEMENTATION / NO TASK GENERATION OR EXECUTION.** Preserve the frozen feasibility target: **40 acquisition groups, 20 per family, plus 20 feasibility groups, 10 per family**, group-disjoint after transitive overlap checks; future confirmation is separately designed and budgeted. Actual valid groups, engine compatibility, trusted custody and historical/pretraining overlap are **UNKNOWN**. This is not a ready scientific experiment.

The existing four CLEAN variants and transport factor tuples are largely common-template cases. The expansion below changes the number of target objects, the source/target relationship and the destination/target relationship in addition to changing the required processing predicate. These graph differences can create genuinely distinct *potential* task structures; they do not prove independent samples or avoid leakage. In particular, source/destination identity renaming, door-state variants and paraphrases are not additional scene graphs.

## Common task specification

Use only the existing pinned public ALFWorld PDDL/grammar and frozen environment; no new environment, policy, prompt, recovery semantics, decoding, or dataset access. The two proposed families are:

- **CLEAN-DELIVER:** for all targets `o_i`, final `(isClean o_i)` and `(inReceptacle o_i d_i)`.
- **HEAT-DELIVER:** for all targets `o_i`, final `(isHot o_i)` and `(inReceptacle o_i d_i)`.

For scene size `n` (1–5), declare one agent, `n` clearly distinguishable pickupable targets, one or more source receptacles, one or more destination receptacles, and one processing receptacle. All sources are at distinct source locations, all destinations at distinct destination locations, and processor is at its own different location; source and destination receptacles never alias. Several objects may begin in one source and several may share a destination, according to the graph below. The actor begins at the processing location with empty hand. All target-processing and destination-goal predicates begin false; each target is in exactly one source. Sources/destinations are initially accessible and, if openable, opened. Processing receptacle has `SinkBasinType` for CLEAN or `MicrowaveType` for HEAT; corresponding target has `cleanable` or `heatable`. Each target/destination pair has a true and unique `objectType`, `receptacleType`, and `canContain` binding accepted by the domain. No irrelevant objects are required. Target labels must be uniquely groundable in actual observations and complete instructions; use meaningful object types rather than claiming different display names prove novel support.

This constrains candidate dependencies to `source_i → pickup(o_i) → process(o_i) → put(o_i, destination_i)` for every `i`, with global single-hand capacity and navigation to the required receptacle. `PickupObject`, `GotoLocation`, `CleanObject`/`HeatObject`, and `PutObject` have explicit preconditions in the pinned public domain. The current HEAT operator does not require a microwave open/close action; only tested production behavior can establish whether that symbolic path is supported in the intended runtime. Target names and correct pairing must be rendered truthfully for *all* conjuncts. A single partially achieved conjunct must not be reported as task success.

## Five structural scene types

Represent a scene by two set partitions of target indices: `S` groups targets sharing a source; `D` groups those sharing a destination. Their joint structure—not the arbitrary index labels—determines the role graph. In each case all location types and preconditions above apply, and each target's independent PDDL goal is one processing predicate plus the corresponding destination predicate.

| Type | Objects and containers / dependencies | Example structural choices for S and D (roles only, not tasks) | Predicted symbolic steps per complete script |
|---|---|---|---:|
| 1 | 1 target, 1 source, 1 processor, 1 destination; one process-and-place chain | S=`{1}`, D=`{1}` | 6 |
| 2 | 2 targets; 1–2 distinct source containers and 1–2 destination containers; two one-hand process/place chains | e.g. shared source, separate destinations; or separate sources, shared destination | 12 |
| 3 | 3 targets; 1–3 sources and 1–3 destinations; three independently required target/goal pairs | e.g. 2+1 in source vs 1+2 at destination, with which target participates encoded in the joint graph | 18 |
| 4 | 4 targets; 1–4 sources and 1–4 destinations | e.g. source groups 2+2 vs destination groups 3+1; assignment intersections are part of the graph | 24 |
| 5 | 5 targets; 1–5 sources and 1–5 destinations | e.g. source groups 3+2 vs destination groups 2+2+1; intersection pattern matters | 30 |

These are **predicted bounds, not observed real step counts**. Under the stated world graph and pinned single-hand operators, each object requires one pickup, processing action and put, and three moves (current location → its source → processor → its destination); the next source is always a different location from the preceding destination. Thus the explicit proposed script has `6n` steps. `3n` object operations plus `3n` moves is also a conditional symbolic lower bound if no other public-domain action can satisfy or shortcut any of those predicates, each target starts unprocessed/in its source, all relevant locations are genuinely distinct, and the domain has no initially held target; an independently implemented operator audit and exact shortest-path check must confirm it. If any assumption fails, record lower/upper as UNKNOWN and reject or revise; never rely on the arithmetic as an engine result. PDDL numeric action cost is different from physical action steps. `30 < 50` for the proposed maximum but instruction length, model context, engine commands, time and task difficulty remain unmeasured.

## Support arithmetic and principled grouping

Before any candidates exist, counting **only the abstract pair of set partitions modulo a joint target permutation** yields the following role-graph shapes: `n=1: 1`, `n=2: 4`, `n=3: 10`, `n=4: 33`, `n=5: 91`; total **139 abstract shapes per processing predicate**. `count_abstract_graphs.py` and `abstract_graph_counts.json` contain the complete bounded combinatorial calculation, with no task, trajectory or random seed. This is not a count of real games, solvable cases, distinct generalization units or independent groups. Goal-blind cross-family matching could pair the same shape between CLEAN and HEAT; other declared near-duplicate edges can merge still more. If insertion/removal of one target is defined as a near-duplicate relation and transitive closure is used, many or all shapes may connect; the remaining support could be far smaller than 60. Neither 139 nor 278 can be advertised as 139/278 independent examples.

Freeze before model outcomes a complete role-typed graph containing all actors, objects, containers, locations, goal-role edges, initial state and action dependencies. Compute exact typed graph isomorphism modulo permissible renaming while preserving source/destination/processor roles, individual target↔destination relations, preconditions, effects and goals. Require collision resolution by graph equality, not hash equality alone. In addition define a goal-blind near-duplicate graph that flags common concrete source cases, paraphrase/descendant, identical setup or substantial role-aligned subgraph/action sequence even across families. Thresholds, edge reasons and any review policy must be specified ahead of time; ambiguous comparisons are UNKNOWN. Compute transitive connected components across all admitted candidate graphs and both families. Do not arbitrarily treat all shared domain, processing predicate or abstract family membership as a forbidden edge. Conversely, do not make semantically related instances independent by hiding a concrete parent under an abstract family node. A post-hoc threshold selected to reach 60 groups is invalid.

To support **40 acquisition + 20 feasibility**, choose 60 *different components overall*, with 20 CLEAN + 20 HEAT for acquisition and 10 CLEAN + 10 HEAT for feasibility, while retaining family/complexity mixture and a frozen unbiased draw rule. Components spanning both families are still one component and can be assigned to at most one split; verify the requested per-family allocation is actually feasible with an explicit component-to-split assignment, not by adding per-family group counts. If overly broad grouping or exclusions prevent it, stop or freeze a genuinely different exploratory design with truthful claims; do not copy/rename candidates or use feasibility data for acquisition.

## Budget and explicit conflict with prior 5-step validation cap

The earlier feasibility proposal permitted at most 200 development-only validation attempts, one construct/load/reset and **five** action steps each. This proposal's 6–30 steps per candidate would exceed that cap even for the smallest scene; no implementation or reviewer may silently use it. Under a separately reviewed proposed ceiling of ≤200 candidate witnesses and ≤30 action starts each, the outer cap would be **200 constructs, 200 loads, 200 resets and 6,000 action starts = 6,200 reset-plus-step starts**. For 60 witnessed candidates it would be ≤60 resets + 1,800 action starts = 1,860 operations, but rejected/failed candidates, up to 200 total attempts, must also be charged. Static attempts, parser/compile/translation/native work, CPU time, memory, disk, monitoring, timeout/cleanup and any started-but-unsettled external operations need separate explicit caps. The original feasibility's 8,540-operation subtotal used 1,200 for five-step validation; replacing that one item with the hypothetical 6,200 yields **13,540** only if every other original cap and accounting definition remains unchanged. This is an illustrative revision, not a frozen or complete budget, and it excludes training/resource/unknown tails just as the original subtotal did. Record actual historic costs separately without double counting.

No new task support, scientific improvement, real runtime reachability, statistical power, GPU fit or authorization is implied. Stop if fewer than 60 qualifying disjoint components with the required per-family allocation are demonstrated, custody is insufficient for the stated claim, any goal/command is ambiguous, provenance is unknown under the frozen policy, resource caps cannot be enforced, or attempted operations are unaccounted for.
