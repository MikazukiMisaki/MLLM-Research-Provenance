## Tested behavior

- An independently fabricated baseline with all four declared partitions and two families returns `NO_DECLARED_CONFLICT`, while `independence_proven`, `custody_verified`, and `claims_verified` remain false. For each of eight partition/family cells, independently setting its only family to null, removing its only record, or increasing its minimum beyond its declared distinct digest count yields UNKNOWN. A boolean minimum also yields UNKNOWN; duplicate digests are not independently counted twice in a cell. The supplied minima are arbitrary positive declarations: one per cell in the test is not the study's proposed 10-per-family feasibility/confirmation floor or a power guarantee.
- Each of the three shared abstract node kinds (`family`, `domain`, `grammar`) alone is permitted across partitions. A directly shared node in any of the three specific kinds (`task`, `task_derivation`, `near_duplicate`) produces `BLOCKED_DECLARED_CONFLICT`. Near-duplicate template connectivity and shared canonical digests remain separate declared-conflict mechanisms. Correctly classifying a node as broad or specific is a submitter responsibility; a false broad classification or omitted relation is not detectable by this tool.
- Twenty-seven fabricated two-broad-node bridges covering every combination of broad/broad/specific node kinds, where one record reaches a specific ancestor through the broad chain and another reaches that ancestor directly, all produce UNKNOWN, not a clean result. Missing nodes and unknown parent status produce UNKNOWN, a self-cycle is rejected, and duplicate JSON keys in the CLI produce INVALID_INPUT. The original synthetic tests also cover transitive ancestry, cycles and family/partition incompleteness.

## Typed-bridge reporting limitation

`lineage_validator.py:127–135` stops ancestor traversal at a broad node. `:103–107` detects any declared broad-to-specific parent edge and sets `BROAD_NODE_HAS_SPECIFIC_PARENT`, so the bridge examples are fail-closed as UNKNOWN. Because traversal is cut off, `declared_conflicts` can nevertheless be empty even when the **declared full graph** contains an explicit path to a specific ancestor shared across partitions. This is not a false `NO_DECLARED_CONFLICT` in the exercised examples; it is a limitation of completeness/severity of reported known conflicts. If callers need conflict enumeration, traverse through broad nodes while excluding broad nodes themselves from the intersected specific-ancestor sets, and separately retain the ambiguous broad-parent UNKNOWN; specify precedence and test it. Never treat empty conflict list plus UNKNOWN as a clean separation.

## Interpretation limits

The tool checks internal declarations and syntactic identities, not the truth of node types, relation completeness, source lineage, semantic near-duplicates, outcome-blind construction or actual task/seed isolation. A shared broad node marked `domain` cannot itself establish that two derivations are unrelated; excluding it is only a proposed taxonomy. A digest/hash binds submitted bytes, not an assertion that data were never previously exposed, and distinct digests need not be distinct semantic families. The schema has no independent custody mechanism, history/pretraining exposure check, trusted data source or statistical power test. A second shared-account process is not independent custody by itself. The output's `NO_DECLARED_CONFLICT` must remain a declaration-consistency status, not a real execution or held-out-independence approval.

No actual or historical task/trajectory/seed, model, GPU or environment was accessed or generated in this review. The synthetic CLI only received constructed metadata.
