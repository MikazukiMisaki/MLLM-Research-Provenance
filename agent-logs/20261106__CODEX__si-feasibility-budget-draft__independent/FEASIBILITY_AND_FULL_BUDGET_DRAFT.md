# Twenty-draw paired feasibility and complete-budget draft

Status: `DRAFT_NOT_FROZEN_NOT_READY_FOR_EXECUTION`. This is a concrete candidate for independent scientific, implementation and resource review. It uses no historical or reserved task contents, trajectory contents or seed values. The twenty draws below are prospective, not completed evidence. Training and collection are prerequisites, not already available or released. A model/environment engineering probe is a separate cost and is not a feasibility study.

## Purpose and minimal admissible conclusion

The proposed study asks whether an independently isolated, three-checkpoint paired workflow can be run and audited end to end, and whether the proposed intervention can be implemented as designed. It does not test efficacy, establish harm/noninferiority, or provide confirmatory evidence. A nominally positive C4−P0 direction in 20 draws is descriptive only; do not use its significance or a favorable observed delta as a gate to declare success. A prespecified adverse signal can motivate stopping or redesign, but cannot establish a population effect. No numerical efficacy threshold is scientifically justified from the pilot alone.

Candidate eligibility before model evaluation, all required:

1. Freeze the permitted self-authored task generator, grammar, two declared families, validity checks and separate development/collection, feasibility and future confirmatory lineage supports. The proposed operational floor is at least ten distinct canonical tasks in each family in the feasibility support and separately in the sealed confirmatory support. This floor is a screening requirement, not a claim that these tasks span ALFWorld or yield independent task families. Verify lineage using a separately reviewed canonicalization, paraphrase/template and generator-input ancestry rule; independent reviewers must validate the rule itself and record unresolved duplicates. No task in a descendant lineage can cross development/collection, feasibility or confirmatory boundaries. Confirmatory support and its draws must remain inaccessible to people/processes tuning on development or feasibility outcomes; prove custody and permitted access, not merely a directory hash. No claims about unknown pretraining or historical exposure.
2. Select exactly ten feasibility draws from each frozen family support by a preregistered selection rule and privately generated random streams. Say explicitly whether sampling is with or without replacement; retain duplicates if the former, without treating them as distinct canonical tasks. Ten-per-family is stratification for feasibility; it differs from IID family mixing and its simple unweighted mean applies only to the specified 50/50 family mixture. Freeze task weights and record rejection attempts; use treatment-independent validation and budget all rejected candidates. Avoid changing family weights by unrecorded rejection. Avoid claims that 20 selected draws imply 20 independent underlying families.
3. Define the environment-randomness target and seed-generation/custody procedure before draws. One independent environment-seed draw per task draw, shared across the three arms when the runtime's randomization semantics make pairing meaningful, is a candidate; common seed values do not prove equal environments, streams, or deterministic replay. Record seed commitment and integrity with restricted raw access, verify initial state/action mapping compatibility and disclose any stochastic process for which comparability cannot be established. If an arm can consume different numbers of random draws, document that common initial seed does not guarantee identical later randomness. Arm execution order is randomized by an independent declared stream (or use preregistered balanced ordering) and logged. These streams and reset identities must be separated from checkpoint, task-generation and training RNG. Actual randomness and independence remain unverified.
4. Authenticate frozen P0 and one prespecified final C1 and C4 checkpoint, source code, runtime, decoding, masks, max output, horizon and interface. C1/C4 must start from the same P0/optimizer configuration and use the same data, tokenization, dose, order and training parameters. Bind the actually realized schedule, checkpoint outputs, and RNG construction; seed equality alone is insufficient. Only the preregistered C4 weights vary. The common dataset needs audited record provenance, trustworthy labels and `0<K<M`; otherwise there is no proposed weighting contrast. Distinguish P0-generated corrections from human, planner and external-model corrections, with acquisition costs and source labels; training on external fixes supports assisted improvement, not purely autonomous self-improvement. Existing synthetic weighted-loss checks do not establish a ready real-data trainer.
5. Before using any model/ALFWorld, independently review implementation, complete the budget table below with enforced numerical ceilings and shared-device/CPU/storage monitoring, reserve the global cumulative allowance and freeze the stop rule. Confirm frozen P0, checkpoint hashes, allowed source and runtime placement in the actual run. No presumed 24-GiB free floor or software test alone proves 8B fit. Keep independently controlled run identities, raw append-only physical receipts and provenance.

Candidate feasibility execution: exactly 20 planned paired draws × three arms = at most 60 episodes. Each episode permits one reset and at most 50 action steps, with at most one model generation per action decision; any special initialization or additional model call must be explicitly counted and included in the budget. Use one fixed horizon and output semantics across arms. An invalid action is an observed non-success only if it is a normal policy event and a frozen parser/termination rule says so; log raw output, validation and termination. Environmental construction/load/compile and translation work are distinct from reset+step and must be measured or bounded separately. Production mapping, prompting and parsing checks must precede any conclusion.

`FEASIBLE_FOR_CONFIRMATORY_PLANNING` requires all 60 episodes and expected receipts, exactly one measured outcome per arm/draw, verified identities/custody and pairing, audit of all completed and started/failed physical operations, verified checkpoint/training contracts, no unresolved missing outcomes or cost tails, no unapproved extra calls, and independently confirmed resource/cap compliance. Report within-family and total per-arm successes, paired win/loss/tie counts, budget and invalid-action rates descriptively, with no efficacy or generalization claim. This result only permits preparation of a *separate* future confirmatory protocol and budget; it does not authorize or establish its feasibility. If the feasibility outcomes change treatment, support, selection, stopping or analysis, freeze the revised choice and use fresh confirmatory support without pooling pilot outcomes. If such changes invalidate support sealing, replace the confirmatory support rather than reusing it.

`TECHNICALLY_INCOMPLETE`: infrastructure failure, broken lineage/receipt, nonfinite model output that is not a declared policy termination, missing outcome, unobservable required resource, mapping mismatch, budget breach, lost monitor or unsafe device condition. Stop, preserve all physical cost and output, and make no 60-episode feasibility-PASS or automatic retry/replacement. Treat an operation whose start is recorded but end is unknown as unknown, not as zero cost; use a reviewed conservative upper bound only if justified. No outcome-dependent omission or selective complete-case inference. A run that completes can still be outcome-selectively observed if technical completion depends on task or treatment; feasibility completion alone cannot justify nominal conditional coverage or remove bias.

## Full-budget accounting: variables and bounds

All caps below are proposals, not authorization or measured consumption. Reserve **separate** limits for setup, authoring/validation/rejection, acquisition, training, evaluations, teardown, technical failures and unknown tails. The study may start only after credible numerical values are frozen for *all* applicable rows and checked against actual cross-run cumulative budgets. Cost units must never be combined across generations, reset+step, CPU/GPU seconds, bytes or training tokens. `≤` bounds depend on enforcement in the actual integration; extra/multiple calls must have their own allowances rather than being ignored.

| Stage | Generation, environment and token accounting | Other required resources and currently unknown values |
| --- | --- | --- |
| Task authoring and candidate validation | `G_task = sum(actual validator/author calls)`, `R_task`, `S_task`, `T_task_in/out`; synthetic grammar validation may require compile, construct, load, reset or step separately. Reserve hard attempt/rejection caps. | Counts of attempts, accepted tasks, rejection rates, instances/lineage checks, compiles/loads/translations, CPU/wall/storage and whether any model assists are **UNKNOWN**. Fixed support is not available merely because a grammar exists. |
| Common experience acquisition and verification | Let `E_A` be attempted episodes, per-episode `h_A`, and `q_A` max generations per decision plus explicitly capped corrections `G_c`. Then `G_A ≤ E_A*h_A*q_A + G_c`, `O_A ≤ E_A*(1+h_A) + O_c`, where O counts reset+step; tally constructs/loads and every completed, failed or incomplete operation separately. Record external model use and `T_A,in/out` from each caller; allocate source-specific limits. | `E_A`, `h_A`, `q_A`, `G_c`, `O_c`, accepted pool size M, target count K and correction success/acceptance rates **UNKNOWN**; no prior illustrative 2,000/2,530 ceiling is an observed cost or current budget. Validation may consume resources beyond these expressions. |
| Two real training arms | Let ordered occurrence set `D_e` represent epoch e; `N_occ = Σ_e |D_e|`; `B` maximum occurrences per optimizer window, after defining final partial window. For full sequential epochs, steps per arm `U = ceil(N_occ/B)` if windows can cross epoch boundaries; otherwise `U = Σ_e ceil(|D_e|/B)`. With fixed M records for E epochs these become respectively `ceil(E*M/B)` or `E*ceil(M/B)`. Two arms use `2*N_occ` example forwards/backwards and `2*U` optimizer updates if no failed work; reserve evaluation/checkpoint saves/load/validation separately. | M, K, E, B, ordering, truncation/padding/masking, updates, gradient accumulation, actual trainable bytes, checkpoint/optimizer storage, CPU/GPU model-loading overhead, peak memory, watts, device hours and exact accepted token counts **UNKNOWN**. Training forward/backward is not an inference generation and has no environment cost by definition, unless separately declared validation invokes one. Count each arm's actual input, padded and active supervised tokens separately; if token count is `t_i`, padded `p_i`, active `n_i`, use totals `Σ_occ t_i`, `Σ_occ p_i`, `Σ_occ n_i` per arm. A numeric upper bound requires a frozen max sequence length `L` and verified padding implementation; then each count is ≤ `N_occ*L` per arm, subject to explicit accounting for any special-token/validation overhead. Do not assert equality between padded and active counts. |
| Twenty-draw paired evaluation | `N=20`, `A=3`, `H=50`, one reset per episode and at most one generation and one step per decision: `G_eval ≤ N*A*H = 3,000`; `O_eval ≤ N*A*(1+H) = 3,060`, composed of at most 60 resets and 3,000 steps. Constructors/loads/translations tracked separately, count **UNKNOWN**. With actually enforced per-generation limits `L_in` and `L_out`: `T_eval,in ≤ 3,000*L_in` and `T_eval,out ≤ 3,000*L_out`. The earlier single-probe limits 4096/64 are illustrative only; they are not a frozen episode policy. | Actual calls, prompt lengths, early termination, model load count, duration and resources **UNKNOWN**. If policy generates more than once per step, retries, diagnostic generations, or prepended warmup calls, these ceilings are invalid unless a separate cap explicitly covers them. Cost of an invalid action depends on whether a physical step was actually called. |
| Technical failures, monitor and teardown | `G_fail`, `O_fail`, token and resource tails are additional to successful-stage caps, not zero. No automatic retry: reserve a bounded safety tail or stop-before-start if unable to bound it. Count all started/finished work and unknown work separately. | Timeout/kill latency, in-flight generation maximum, environment operation completion, telemetry lag, final checkpoint/synchronization and output flush, CPU/GPU deallocation, and safe behavior on monitor failure **UNKNOWN**. A decision to halt does not retroactively undo calls already started. |

Prospective totals are `G_total = G_task + G_A + G_eval + G_fail`, `O_total = O_task + O_A + O_eval + O_fail`, plus **separate** training forwards/backwards, updates, tokenizer/token units, model-load/construct/load/compile counts and resource ledgers. Include model calls during training evaluation/checkpoint selection as separately capped terms if present. Token totals sum each stage's *actual* input/output tokens and failed/unknown bounds, not counts inferred from a single 189-token engineering state. Physical environment operations are counted once at their real boundaries, not by adding logical wrappers. Preexisting project usage is a baseline, not another copy of stage totals. Separately distinguish all-project totals from the known subset; do not assert the subtotal exhausts prior costs.

GPU allocation cost is `Σ_jobs ∫ [allocated devices] dt` (device-hours after division by 3600); device-wide sampled memory/utilization are not necessarily attributable to this study on a shared GPU. Track actual job wall time and CPU-seconds, host and device peak memory, disk/network I/O, storage and monitor cadence; do not sum overlapping multi-job wall times as elapsed time. Hard limits must be set independently for elapsed time, device-hours, host RAM, GPU memory, output storage and every measured call/token class, with a technically justified stop tail. Neither model-file size nor a one-byte CUDA smoke test establishes real model loading/training fit. If ownership or cleanup is uncertain, mark it unknown and avoid interfering with others.

## Acceptance and resource-release consequence

Study remains **NOT_READY**: actual C1/C4 training on an approved common pool, independently isolated task supports, true producer/consumer pipeline, complete numeric caps and empirical resource fit are not established here. The path to a legitimate small study is to freeze audited lineage/custody, create and validate the common pool, independently test weighted training and accounting, establish real checkpoint and inference fit with a separately bounded engineering probe, fill every budget row, and independently review the exact frozen implementation/protocol. Only then can the bounded 60-episode feasibility plan be considered. The former engineering checks, the fixed-N arithmetic, and any future 20-draw descriptive outcomes must not be relabeled as proof of success-rate improvement.
