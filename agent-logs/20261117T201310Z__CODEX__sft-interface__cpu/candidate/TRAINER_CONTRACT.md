# Static review of existing SFT interfaces

This is a code-only review; no model, tokenizer, environment or real training example was accessed. Exact paths and hashes are in `source-hashes.json`; these are two distinct implementations with different contracts, not one interchangeable trainer.

## Repository baseline: `src/sft/training.py`

`train_lora` reads JSONL rows filtered as train and validation with string `prompt`/`completion`. Its local precheck tokenizes prompt and prompt+completion with special tokens, adds EOS text when missing, requires the prompt token IDs to be a prefix, refuses sequences above configured `max_length`, and computes completion-only masks. The specific checked-in run config pins 2048 total tokens, not 4096. It passes only prompt/completion strings to `SFTTrainer`, which retokenizes; the code does not pass v7 `input_ids` or `loss_mask` into the trainer. Consequently the code review alone cannot assert that v7's token IDs/mask survive this path; actual TRL/tokenizer behavior would require separate verification. The no-truncation claim here is the local precheck, not a separately verified TRL internal behavior.

This baseline initializes Qwen3-8B base weights afresh, then creates a LoRA adapter r32, alpha64, dropout .05, all-linear, BF16. The checked-in run config specifies fused AdamW, lr 1e-4, batch2 × accumulation8, two epochs, cosine schedule, completion-only loss, no packing; train/eval arguments are passed to SFTTrainer. It saves `final_adapter` and tokenizer plus training result, with smoke-only reload check. This path does not initialize from an existing P0 adapter by its visible code.

## Research candidate: `native_update.py` and `source_handoff.py`

`run_one_update` accepts exactly four immutable `Row(prompt: tuple[int,...], generated: tuple[int,...])` objects plus a reviewed, recipe-bound selection handoff and reviewed configuration. It requires nonempty token sequences, generated length <=16 and combined prompt+generated <=4096. It reconstructs labels as `[-100]*len(prompt)+generated`, so it does not directly consume an arbitrary supplied mask: exact preservation holds only if separately established that the input mask is exactly zeros for the whole prompt followed by ones for every generated token. It then calculates shifted causal cross entropy with ignore_index -100, summed and normalized over active generated tokens, EOS included. It validates vocab and eligible EOS/pad, model trainable LoRA names and P0 LoRA r32/alpha64/dropout .05. It uses fresh P0 producer per documented contract; the candidate checks adapter presence and architecture while the loader/owner must bind exact identity. It sets seed and mode, performs one fresh AdamW optimizer step over four microbatches and writes a safetensors adapter checkpoint. Research stage config pins lr3e-5, betas (0.9,0.999), epsilon 1e-8, weight decay0, non-fused; readback/reload is separately performed by stage composition. These values describe the existing candidate, not a new experiment design.

4096 is the candidate's software row limit; actual loaded model positional limit, memory feasibility, version compatibility, product identity and real runtime remain unobserved. No evidence from this review establishes that an actual model can train at this length.

## v7 compatibility

The selector's target/control JSONL rows include `selection.label`, `selection.loss_mask`, `selection.input_tokens` and the decision's prompt/action/label/mask references; the output itself does **not** include the full prompt IDs or the whole sequence. A future reviewed component would need the exact authenticated referenced artifact bytes and identities, the original source/review chain, and verified vocabulary/EOS/tokenizer bindings before reconstructing the selected token row. A hash of a user-supplied artifact and self-declared `AUTHENTICATED` cannot prove provenance.

Neither the baseline text trainer nor the current research `load_reviewed` function directly accepts the v7 selector output: the research handoff has its own fixed source/review and selection schema, recipe, exact four-row requirements and reviewed source constraints. It would be incorrect to label a v7 JSONL or the two-row fake preview as runnable training input. Minimal future compatibility would be a separately reviewed provenance-bound v7 resolver, explicit completion-only mask equivalence and full-sequence/no-truncation checks, a reviewed four-row batching/weighting and recipe contract, precise product and tokenizer identity, and a supported trainer interface accepting those exact token IDs/labels. That work remains unimplemented, and actual training stays HOLD.
