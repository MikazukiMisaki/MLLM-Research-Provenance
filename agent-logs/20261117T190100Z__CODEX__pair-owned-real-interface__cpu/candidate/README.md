## Implemented source to review

- `fixed_product_dev/arm_stage.py` is a modified copy of the existing worker-stage interface. It removes arm-local materialization and accepts one parent-created pair binding containing the same absolute game/config/data-root paths plus game/routing/config hashes. It checks containment and hashes and invokes the existing port's pre/post verification. This is path/hash checking, not immutable isolation. `fixed_product_dev/episode.py` remains byte-identical to the previous source.
- `fixed_product_dev/worker.py` adapts those arguments and the four-materialization plan, but its `main()` **always raises RESEARCH_HOLD** before argument parsing or any model/environment work. The old worker and old supervisor are not rewired and must not be launched.
- `fixed_product_dev/arm_budget.py` is a modified copy of the existing StageBudgetChannel: the per-arm profile no longer requires materialization and forwards validated reserve/return operations to one candidate global owner. The parent's journal record is fsynced before an ACK; unknown, malformed frames, EOF and send errors latch failure. Operation and local caps are retained. The actual nonblocking scheduler and its ACK deadline must still be integrated and reviewed.
- `global_owner.py` implements a single append/fsync global ledger, prescribed four case/arm order, four-setup cap, pair binding, per-arm/global operation caps, and parent checking of returned reset child claims before model-load reservation. The first/second claim comparison is defined in the owner; **the actual transition to a second arm is currently hard-blocked** because independent process-tree cleanup has not been implemented. There is no complete batch scheduler, no working advancement across cases, and `complete()` always fails closed. Do not treat the first-arm test as a two-arm or four-pair integration result.
- Per generation, the candidate expects exactly one unconsumed hash-chained child `prepared` record, validates its claimed IDs/mask and fake-or-real claimed decoding config, then reserves **4096 input plus 16 output tokens**, the full frozen per-call upper bounds, in the same fsynced reservation before ACK. It never refunds the conservative reservation. On a returned child claim it checks the bound prepared digest, claimed input prefix, output IDs and shape; unreturned reservations remain charged. This requires the separately verified frozen worker actually enforces the per-call bounds and assumes a trusted worker. A child journal is a claim, not independent proof of actual physical tokens or defense against malicious same-UID mutation. Actual tokenizer/device preparation already precedes the generation reservation. Total reserved caps are `400*4096` input and `400*16` output. The code is not a production clearance, and real-worker/source identity, input authenticity and trustworthy resource supervision remain unresolved.
