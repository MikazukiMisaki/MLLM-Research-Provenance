## Four groups and their causal signatures

A group denotes a predeclared mechanism family, not multiple statistically independent samples. Each suggested trace is a source-level witness, not an observed plan, parser acceptance, grammar rendering, or proof of runtime solvability. Actor locations, closed-world negative facts, types and receptacle compatibility must be explicitly bound in any later case draft; ambiguous names or missing action mappings mean stop.

### A. Two processing goals on one held object, then closed-container placement

**Goal:** `(isClean item) ∧ (isHot item) ∧ (inReceptacle item cabinet)`. Start actor beside the source with one pickupable, cleanable, heatable item in a non-openable source; source, sink, microwave and closed openable cabinet are at four pairwise distinct named locations; cabinet type can contain the item type. Initially neither processing predicate nor cabinet-opened is present.

Source-level witness, eight actions: take item; go sink; clean with sink; go microwave; heat with microwave; go cabinet; open cabinet; move item to cabinet. `CleanObject` and `HeatObject` each require holding the same item and the correct appliance type; both goal effects must survive until placement; `PutObject` requires an open or non-openable receptacle and matching containment types. Clean and heat commute under the inspected effects, so the chosen order is a witness, **not a claimed mandatory clean-before-heat edge**. This is a two-transformation conjunctive mechanism, unlike the previous heat-only task, while retaining a disclosed common family lineage.

### B. Tool-dependent slice and compulsory hand exchange

**Goal:** `(isSliced item) ∧ (inReceptacle item shelf)`. Start actor at a non-openable worktop with distinct pickupable knife and sliceable, pickupable item both in/on the worktop; both have the corresponding location. Knife has `objectType KnifeType` (or the separately fixed ButterKnifeType). Worktop must be able to contain the knife type for putting it back; shelf must contain the item type and be non-openable or already open.

Witness, six actions: take knife; slice item with knife; move knife back to worktop; take item; go shelf; move item to shelf. `SliceObject` requires item at the actor's location and the typed knife held. `PickupObject` requires no object already held, so the subsequent target pickup requires releasing the knife first. This tool-exchange dependency is structurally different from appliance processing. The exact runtime grammar strings and `_valid_actions` groundings are unverified.

### C. Two objects compete for one held-object slot and one cooling station

**Goal:** `(isCool item1) ∧ (isCool item2) ∧ (inReceptacle item1 shelf) ∧ (inReceptacle item2 shelf)`. Start actor at the fridge, two distinct pickupable/coolable objects in the same non-openable source at a different location; shelf at a third location is accessible and may contain both object types; fridge has `FridgeType`. Neither object is initially cool.

Witness, twelve actions: go source; take item1; go fridge; cool item1; go shelf; move item1 to shelf; go source; take item2; go fridge; cool item2; go shelf; move item2 to shelf. The `holdsAny` precondition forces the two physical carries to be sequential; either object may go first, so the example order is not an imposed asymmetric causal dependency. `CoolObject` requires a held coolable item and fridge at actor location. This group adds resource contention and repeated handling of distinct objects rather than merely duplicating names in a single-object task.

### D. Independent toggle goal plus carrying into a closed container

**Goal:** `(isToggled lamp) ∧ (inReceptacle mug cabinet)`; task text should say **use the lamp and put the mug in the cabinet**, without implying any required order or that the lamp must remain on. Start actor at table with a toggleable lamp and pickupable mug in/on the table; lamp is initially not toggled and not on, and cabinet is closed/openable with a compatible mug type at a separate location.

Witness, five actions: use lamp; take mug; go cabinet; open cabinet; move mug to cabinet. `ToggleObject` requires the lamp in its co-located receptacle and sets `isToggled`; pickup/place is a distinct conjunct and the one preselected trace has no policy-dependent choice. The two conjuncts can be achieved in different orders, so the mechanism is parallel goal satisfaction, not a claimed dependency of mug placement on the toggle. **Source caveat:** public toggle feedback tests `isToggled` when choosing the phrase “turn on”; after a later second toggle, that wording need not describe `isOn`. This protocol's fixed witness toggles only once, and any later free-agent episode must retain actual facts and feedback rather than assume the narrative proves on/off state. No code is altered to hide that behavior.

## Frozen initial-state consistency for every later concrete case

Each v1 template has exactly one actor and pairwise distinct role objects and receptacles; every role has one declared type, and source, processor/appliance and destination locations intended for navigation are pairwise distinct within its template. Actor is at exactly its stated start location, with no other `atLocation` for that actor. No `holdsAny(actor)`, no `holds(actor, x)`, and no other holding relation involving a task object is initially present. Each task object is initially in exactly its declared source receptacle, at exactly that source location, and not simultaneously in the destination or another receptacle/location. B's knife and target and C's two items must be distinct, as must D's lamp and item. No contradictory positive facts or undeclared aliases are allowed; uniqueness of identifiers alone does not establish these facts.

Every individual goal conjunct must be false initially: A has no `isClean`/`isHot` and item not in destination; B no `isSliced` and target not in destination; C neither item `isCool` nor either item in destination; D no `isToggled` and item not in destination. Openable destinations begin unopened. B's worktop is fixed **non-openable** for this version, which satisfies the reviewed “non-openable or already opened” disjunction without selecting between alternatives. The source-level fixed witness assumes these exact facts, closed-world absence, valid types and `canContain`; it is not a real run or proof of runtime grounding.

## Source construction, lineage and duplicate prevention

1. Before any parser/engine/model run, author at most one concrete case per group from these mechanism descriptions. Record the author, date, public domain/grammar hashes, all generation/template inputs, exact problem/grammar/manifest bytes and SHA-256, task text, preconditions and candidate static trace. Use only the public domain and newly authored declarations; do not copy unknown or protected task files/trajectories. Pin domain-referenced typed objects (`MicrowaveType`, `SinkBasinType`, `FridgeType`, `KnifeType`, `ButterKnifeType`) as required by the actual translator or stop on ambiguity. Record grammar marker substitution and retain original public grammar bytes by reference. A hash establishes byte identity, not origin or independence.
2. Assign lineage labels A–D before behavior is observed. A records the earlier heat/drawer conceptual parent; B–D record their explicit mechanism descriptions and any other known sources. Rephrasings, object renaming, location renaming, permutations of interchangeable objects, extra irrelevant facts and reordered conjuncts do not create a new lineage. Parameter variants within a family remain grouped, even with different surface strings.
3. For within-batch duplicate screening, construct a canonical typed dependency graph from the authored objects, initial positive/negative conditions, action-schema preconditions/effects and goal-object incidence; normalize variable/object names and unordered conjunctions, while preserving predicate/action semantics, type roles, multiplicity, causal edges, exclusivity/hand-use and initial/goal status. Collapse equivalent alpha-renamings and permutations. A near-duplicate screen compares the same signatures after stripping declared irrelevant distractors and records edge/object overlap plus a human-readable graph comparison; no numerical similarity threshold is invented post hoc. If a proposed pair's causal signature or provenance cannot be distinguished, treat it as the same group and do not replace it after observing a run. Exact graph comparison is within this author-controlled batch, not a search of protected history; no historical/held-out/pretraining independence claim follows.
4. Define lineage components by deterministic transitive closure over **known** `DERIVED_FROM`, `RENAMING`, `PARAMETER_VARIANT`, `SAME_MECHANISM` and resolved `SAME_CASE` links: ignore edge direction for grouping and union connected nodes, retaining directed parent edges for provenance. Shared use of a public domain alone is not a derivation edge; A and its known heat/drawer conceptual parent are linked. Cross-group members in the same component are not distinct groups. For an ambiguous comparison within the four proposed cases, record `UNKNOWN` and stop batch qualification until resolved without behavior-based decisions. Unknown connections to protected or unavailable history stay UNKNOWN, not a reason to search it and not evidence of no overlap. Group distinction is within the fixed proposed batch; it never establishes global or statistical independence.
5. Freeze group order A→B→C→D, concrete byte commitments, scripted action bounds and stop rules before any feasibility operation. Record missing/invalid drafts and stop, rather than choosing a more convenient generated variant after results. No outcome-dependent group selection, substitutions, seeds, backtracking, reruns or retrospective reclassification. If a later experimental study needs independently sampled tasks, separate unseen custody and an explicit sampling design are required; this development protocol does not establish either.
