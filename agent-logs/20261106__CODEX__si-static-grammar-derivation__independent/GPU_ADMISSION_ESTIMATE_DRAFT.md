# One-action GPU admission estimate — not a measured fit

The target is the pinned local Qwen3-8B BF16 snapshot and previously identified adapter. The model index reports 16,381,470,720 tensor bytes (about 15,623 MiB) and the adapter file is about 333 MiB; these disk sizes are rough weight-scale inputs, not measurements of device allocation. The five separately streamed local shard digests matched their cache references, but their overall verification process exited 1 due to an invalid aggregate comparison; preserve that failure and do not call the entire check PASS. Actual load placement, replication, fragmentation and library workspaces can differ substantially from this estimate.

For context only, the local config states 36 layers, eight key/value heads and head dimension 128. A conventional unquantized BF16 key/value cache for a single sequence of 4,160 tokens would require roughly `4160 * 36 * 2 * 8 * 128 * 2 = 613,416,960` bytes, approximately 585 MiB. Actual cache implementation and lifetime may differ. A full-sequence BF16 logits matrix with 4,096 positions and vocabulary 151,936 would be about 1.16 GiB, if actually materialized; actual model/Transformers behavior, dtype and retained tensors must be verified, not assumed. CUDA libraries, allocation fragmentation, transient weight loading, PEFT, scores and activations remain additional and unmeasured.

An independent source check found that the locally installed Transformers generation code may set `logits_to_keep=1` when supported, and local Qwen3 exposes this argument; therefore the full 4,096-position logits example is not a prediction that such a matrix will be allocated. Its actual behavior through PEFT and the chosen generation path is unresolved. If 64 vocabulary-sized scores are retained, their raw size alone would be about 18.55 MiB at BF16 or 37.09 MiB at FP32, conditional on dtype and retention. PEFT may autocast adapter parameters, so adapter disk size also does not establish adapter memory.

For a future one-action engineering proposal, **24,576 MiB device-wide free memory before model loading is an intentionally conservative preliminary admission floor, not a demonstrated sufficient peak or reservation**. It is a planning hypothesis requiring independent review of the exact loader, resource policy and current shared-device behavior. The floor is above the weight-scale estimate plus the illustrative cache and logits but does not mathematically bound the unknown overhead. If a future reviewer cannot justify even this provisional risk or enforce a bounded stop and accounting, do not start the model. No quantization, offload, model change, or relaxed floor is implied.

Query total, reserved, used and free explicitly; integer MiB rounding can make their sum differ by a small amount. Use the reported free quantity directly rather than subtracting reserved twice. Recheck immediately before launch and continuously monitor device-wide free memory and the owned process as far as observable, while preserving other users' processes. Free memory may disappear between observations and shared ownership is allowed; this floor is not exclusivity or a scheduler allocation, and device-wide memory cannot automatically be attributed to the worker. If any required measurement or process control becomes unknown, preserve all started/open work and stop only the owned workload. Specify separate remaining-free, elapsed, host-RSS, output and failure-tail policies before a reviewed live worker exists.

At the 2026-11-06 15:08 UTC snapshot, the shared A40 reported total 46,068 MiB, reserved 665 MiB, used 36,920 MiB and free 8,484 MiB with 100% utilization. That is below the hypothetical floor and even below nominal BF16 weight size. This point-in-time observation is not a prediction of future availability. The proposed floor, 4,096-token input limit, 64-token output limit, placement and all actual enforcement remain unapproved implementation details until a distinct exact-byte candidate is independently reviewed. No research model, GPU allocation or environment call was made to calculate this note.

A later read-only host-memory snapshot reported `MemAvailable` 125,115,316 KiB, while the current memory cgroup v1 files reported usage 34,213,584,896 bytes and an effectively unlimited-looking local limit. These snapshots do not establish available process memory: cgroup usage includes cache, parent limits or competing work may be invisible, and available memory can change. The production loader's `device=auto` may use mixed placement; a non-auto CUDA setting first loads through the model loader before calling `.to(device)`, so host memory and the actually realized device map must both be bound and observed rather than inferred from GPU free memory. No alternate placement is approved by this estimate.
