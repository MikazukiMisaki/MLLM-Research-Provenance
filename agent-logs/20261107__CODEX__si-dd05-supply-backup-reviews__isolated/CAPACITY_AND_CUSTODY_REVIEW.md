Status: `DEVELOPMENT_CAPACITY_BOUNDED / INDEPENDENT_CUSTODY_UNVERIFIED`. This is a software/source review, not a release to construct an unseen set, a statistical result, or a scientific run. No protected task, identity, historical inventory, model, planner, or environment was accessed by this review.

## What exists and its actual capacity

The existing publicly sourced development constructor `generator.py`, SHA256 `e589d58547bc250d830dbcda230278849890d7247edaaed065341121cf51b330`, has four explicitly enumerated template groups. Its `_spec` requires one instance of each in fixed order. `build_case` chooses fixed state, goal, and action structures as a function of group; names supply roles, not a new causal family. `FEATURES` and the mechanism signature are also fixed per group. This implementation is therefore not a mechanism for supplying 168 independent parents by repeated batches, renaming, paraphrases or seeds. Four is the number of declared mechanism labels, **not** proof of four valid or independent real task families. The old one-shot has already been used; this review does not rerun it.

As a concrete negative-control check, `test_role_renaming.py` applies the existing `render` function to 100 invented sets of object-role names for each group, with invented inert grammar in memory, and never emits or saves the resulting problems, plans or names. For the 400 fabricated calls it observed one structural-signature value per group and four total. The actual isolated subprocess exited 0; see `test_receipt.json`, `test.stdout` and `test.stderr`. This finite test checks those variations and the implementation-defined signature, not arbitrary semantic equivalence, validity, runtime reachability, population yield, or independence. It is not task-generation, model, parser, planner, or environment evidence.

The prior independently audited B/C witnesses are development-only, scripted observations; the D attempt stopped on a discrepancy between declared and observed selected facts, and the earlier A attempt has its own distinct technical status. None establishes a protected or confirmatory sample. See the separate aggregate audit `20261107__CODEX__si-bcd-attempt-independent-audit__isolated/INDEPENDENT_AUDIT.md`; its task-level material was not used in this review.

## Decision and next executable steps

1. Retain B/C solely for the separately reviewed exposed development comparison. Freeze source/treatment/isolation/resource controls before any run; successful software integration or a 2-case comparison cannot establish improvement or generalization.
2. Do not use the present four-template constructor as a confirmatory population. Build or source a *new* bounded, family-diverse typed constructor and independently evaluate causal duplication, language/goal agreement, domain actions, rejection accounting and actual solver/backend compatibility. The existing four-group constructor, PDDL bridge and graph prototype are useful references, not a validated sampler. Start with a fabricated-only rule/normalizer and a finite candidate-space accounting model; only later admit a separately reviewed bounded development construction and no-model witness budget. Never draw confirmation material under shared access and call it sealed.
3. For confirmation, commission a genuinely separate steward or independently administered restricted storage with audited access; freeze and externally anchor a keyed whole-manifest commitment and have that steward run a single non-oracular overlap check against an authorized historical inventory. The completeness of that inventory and model-pretraining exposure remain separate UNKNOWNs. A coordinator-owned process cannot independently attest the coordinator's nonaccess.
4. If no such custody route or sufficiently diverse valid families become available, continue the same research question as exploratory development with explicit limits, or obtain a separate documented asset; do not silently change same-template instances into independent observations. Before the requested larger comparison, perform exact test power and clustered-family sensitivity analysis under the finally specified population and account for task construction, invalid candidates, failed starts, model loads and full device/I/O costs.

The 168-parent figure is a prior *conditional* calculation for a hypothetical 10-point effect and 20% discordance, not a measured requirement for every study and not a guarantee when families cluster. No new eligible independent parent count has been established.
