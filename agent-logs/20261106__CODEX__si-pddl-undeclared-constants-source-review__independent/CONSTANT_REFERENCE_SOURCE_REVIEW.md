# Domain action constants: source-only compatibility review

**Conclusion: definite undeclared-domain-symbol and static coverage gap; actual installed-parser failure is NOT established.** The pinned ALFWorld domain refers to five fixed symbol strings in action conditions but has no `:constants` section. The four self-authored drafts separately put the one symbol needed by their own selected processing action in the problem's objects and omit the other four. The v3 checker validates its selected scripted actions, not global declaration/typing of all domain action constants. This deserves explicit reporting and an independent checker contract, but the inspected Fast Downward parsing code does **not** justify claiming that all four real drafts necessarily crash or that all five symbols must be added to each problem to run this installed engine. No parser, translator, model, GPU, environment or task execution was run in this review.

## Fixed, directly inspected inputs

Pinned `alfred.pddl` SHA256 `f1473041ed01da514de1f87adfd7ef0804862361f83ccf63c75e43633b0eb280` has no `:constants` declaration. Its `CleanObject` requires `receptacleType(..., SinkBasinType)` at line 405; `HeatObject` uses `MicrowaveType` at 424; `CoolObject` uses `FridgeType` at 443; and `SliceObject` uses `KnifeType` or `ButterKnifeType` at 484–485. In these relations the first three have the predicate argument type `rtype`, the latter two `otype`. All are fixed non-variable argument symbols, not the syntactic `:types` declarations themselves. The self-authored CLEAN-1/2 each declare `SinkBasinType - rtype`; HEAT-1/2 each declare `MicrowaveType - rtype`; none of the four problem object lists declares the remaining four named symbols. These observations concern the public domain and the four explicitly authorized self-authored drafts only.

## What the installed code actually does

1. `fast_downward/interface.py:198–205` calls nested-list parsing, `parse_task`, normalization and conversion. Its tokenizer (`translate/pddl_parser/lisp_parser.py:20–30`) lowercases tokens, so casing differences in these names are immaterial in that parser.
2. `parsing_functions.py:242–262` parses each action's preconditions using `parse_condition`. `parse_literal` at lines 100–116 validates the *predicate name* and argument **arity**, then constructs an Atom from the raw argument strings; it does not consult the problem object table or validate each referenced constant at this point. `parse_domain_pddl` starts with an empty domain constant list at 328–331 and reads a `:constants` section only if present at 353–354. It parses all domain actions at 382–390. Consequently, the absence of those constants is visible from source, but a mandatory parse-time `Undeclared constant` rejection is **not evidenced by this code path**. Other failure paths and native implementation behavior have not been executed.
3. `parse_task` at 295–309 joins parsed domain constants with problem objects and checks duplicate names; `pddl_to_prolog.py:145–157` creates typed-object facts only for `task.objects`. `normalize.py:369–391` retains positive literal conditions in exploration rules, and `build_model.py:38–52` keeps non-variable condition arguments as constant strings for matching. `pddl/conditions.py:263–273` retains unbound strings during substitution and treats an absent static fact as an impossible action instance. Thus an inactive condition referencing one of the missing constants can simply lack a matching `receptacleType`/`objectType` fact under this closed-world translation path; a deterministic crash solely from that absence is not shown. This source-level reasoning does not prove a complete translation will succeed or that pruning has no side effects.
4. TextWorld's `PddlState` calls `pddl2sas` twice (`textworld/envs/pddl/logic/__init__.py:169–172`), builds `name2type` from `task.objects` at 187, and maps atom arguments via `name2type[arg]` at 194 and `get_fact` 131–135. **Conditional risk:** if an actually emitted init, SAS or effect atom contains an undeclared name, the mapping can raise `KeyError`. The inspected source does not prove one of the unused domain-only strings reaches those outputs for these drafts. It is incorrect to report this conditional path as an observed failure.

## Minimum action and consequences

- Before trusting the checker as a complete domain/problem validator, add a separately reviewed static report of **every non-variable argument in each domain action**, its inferred predicate argument type, domain-level declaration, problem-object declaration, reachability/selected-script relevance and resolution status. Add fake negative tests for missing, wrong-typed and duplicate declarations and for selected versus unselected action constants. Declare unsupported expressions UNKNOWN/stop; do not infer global domain validity from a selected script passing. Frozen original drafts, domain and v1–v3 evidence should remain unchanged.
- The selected CLEAN/HEAT action's referenced type symbol is present in each respective problem, so this specific fact alone establishes **no necessary source change for the selected symbolic path under the permissive local parser**. Whether a real full TextWorld/Fast Downward compile, rendering, reset and step succeeds remains UNKNOWN until a separately reviewed, budgeted engine witness is performed.
- If the project requires strict standard-PDDL domain declaration rather than compatibility with this implementation, a *derived*, independently reviewed domain could add all five symbols in `:constants` with their inferred types. This changes the frozen public domain bytes. Corresponding duplicate problem-object declarations would then need removal because `parse_task` checks duplicates; new domain/problem hashes and semantic/equivalence review are required. It must not be done silently or represented as an in-place repair of the frozen domain. Conversely, adding the four missing names as problem objects is a possible compatibility experiment, not proof of standard domain validity and not a proven requirement: it expands the declared object universe, may affect grounding and would also require new hashes, bounded comparison and review. Do not assume such an edit is behavior-neutral.
- Until the checker contract and exact engine compatibility are established, keep the outcome **STATIC_SELECTED_PATH_ONLY / FULL_DOMAIN_DECLARATION_UNRESOLVED**; do not label the existing static PASS as a successful external parser/engine run, or use these drafts as independent scientific tasks. Other previously identified review findings remain pending.
