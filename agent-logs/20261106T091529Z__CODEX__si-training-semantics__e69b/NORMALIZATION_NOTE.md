# Weight normalization and token lengths: synthetic design check

The existing experimental helper uses a fixed fourfold target-to-other example-weight ratio. Its C4 constants 26/7 and 13/14 correspond to normalizing the mean example weight to one for an invented population of 8 target and 304 other examples. The helper computes a microbatch contribution as native mean shifted-token loss times that example's weight times its active shifted-token count divided by the unweighted active-token count for the update. The helper is not a production launcher, and the assumed population is not a verified future dataset.

For an example population of M items with K target items, sample-mean-one normalization gives alpha=M/(M+3K), target weight 4alpha and other weight alpha, if M>0 and 0<=K<=M. This is sample normalization, not generally token normalization. Let target active-token total be U and other active-token total V. The token-weighted mean is alpha*(4U+V)/(U+V), which equals one only under additional relationships between group sizes and lengths. Example M=2,K=1 gives alpha=0.4. If the target has one active token and the other has five, token-weighted mean is 0.6; swapping lengths gives 1.4. The fourfold ratio remains the same. This is invented arithmetic, not a result on any real example.

An alternative precommitted token-mean-one scale would be beta=(U+V)/(4U+V), but it is a different treatment and requires known authenticated token totals and the same masking convention. Per-update normalization would be different again and can change relative scaling and clipping across updates. Do not choose among these alternatives after observing success outcomes, and do not claim that a dataset-wide sample-normalized loss keeps each optimizer update's gradient norm or learning rate equivalent. Finite precision, clipping and adaptive optimizer dynamics add further differences.

For a future authentic comparison, freeze the exact normalization rule, population/counting unit, shifted label mask including EOS, handling of varying lengths and accumulation denominator; verify the actual model's native loss convention and tokenizer behavior with independently checked fixtures; account for gradient clipping, optimizer state and learning-rate schedule. C1/C4 must share the actual permitted data, ordering, initialization, and training dose, with the weighting as the intended treatment difference. If any counts or labels cannot be established within the allowed loader scope, keep the run unready rather than substituting the invented 312/8 values. This note uses no model, environment, protected task or real training data.
