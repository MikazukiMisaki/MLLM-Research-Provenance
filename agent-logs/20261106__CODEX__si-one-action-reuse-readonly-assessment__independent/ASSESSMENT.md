# One-action probe reuse for a two-stage engineering probe

Scope: read-only inspection of the specifically allowed one-action enabled-review directory and implementation files expressly referenced by it. No model, tokenizer, environment, parser, GPU, or historical task/trajectory was run or opened. This assessment does not authorize execution. The one-action run was already consumed and its outcome is only a development interface observation (ROOT_EXECUTION_RECORD.md). A new probe needs a new claim and a new, independently reviewed scope; the old claim must never be reused.

## What can be carried forward as source patterns

* The fixed-owner architecture binds launch context, manifest, source digests, baseline identity and absent claim/output paths before a single child, then records resources, reaps only the owned direct child and verifies local results. See enabled-review `owner.py:122-208,221-298,382-466,489-495`, `bridge.py:152-202`, `release_guard.py`, and `FROZEN_SOURCE_BINDINGS.json`. These are source patterns to copy and adapt, not ready-made authorization for a different target. Fixed identity and self-attested local review/clearance are not an independently trusted security boundary; target checks and creation are not a single atomic transaction.
* Worker parent-death signal / READY-GO and direct pidfd can be adapted (`worker_candidate_v2.py:70-103,107-129`, `owner.py:221-250`). **Necessary correction:** `owner.run_engine` calls `release` (sends GO) before persisting `WORKER_RELEASED` (`owner.py:399-403`). Thus there is no evidence of a pre-GO durable worker-start marker. In the new design fsync a bound start before GO; a GO write failure or owner death thereafter leaves an open UNKNOWN. Test the no-GO-on-fsync-failure and crash windows. Direct child cleanup, PDEATHSIG and pidfd do not settle descendants, already-submitted GPU work or kernel/native tails. The old claim/source/output paths are fixed and consumed.
* `bridge.py:62-118` verifies sampler source/identity and two fresh spaced device/host samples plus free disk; uses GPU admission floor 24,576 MiB, host 32 GiB and disk 2 GiB; periodic checks include device floor, host floor and direct-child RSS. Owner's 600-second work deadline and sampling are best effort, not a bound on setup, cleanup or kernel stalls. Device-wide snapshots aren't reservation or process attribution, sampling gaps and cgroup effective headroom can be UNKNOWN; a new 2-generation memory/time policy must be specified rather than silently assuming the 1-generation thresholds prove fit.
* `worker_candidate_v2.py:204-255` tests one CUDA-visible GPU identity before and after load, checks model parameters/buffers, device map and inspected hooks. This establishes only the observed properties; all native allocations, full offload routes, process ownership and fresh weight bytes remain unproven. `direct_worker.py:140-158` binds specified case, domain, tokenizer auxiliaries and adapter; current model shard evidence is metadata matched to an earlier scan whose aggregate exit was 1, **not fresh content authentication**. Any new probe must independently bind exactly its current self-authored clean-1 inputs and correct model identity, and report provenance limitations. The old source hardcodes `s1-d1-n0.pddl`; this audit has not established it is the requested clean-1.
* Journals and guards give useful START/RETURN and local hash chaining (`worker_candidate_v2.py:145-191`, `direct_worker.py:235-257`, `worker_entry.py:30-48`). A readable terminal record after fsync failure is not independently confirmed durable. Preserve UNKNOWN when the write or fsync/ack is uncertain, do not turn it into completion using another equally untrusted local marker. Separate independent audit and raw receipt should remain separate; no external trust or power-loss guarantee follows from local SHA chains. Counts should report started/returned/unknown separately, never equate missing return with no work.

## Changes required before a new 2-stage candidate could be reviewed

1. Freeze the actual production recovery source, parser, transitive local imports, configuration, prompt and source origin, and the self-authored clean-1 case and domain/manual inputs by exact bytes. This restricted source set does not reference a production two-stage recovery operator; therefore this read-only inspection cannot certify its actual calls, prompts, parser semantics, stage order or adapter support. First establish those on an explicitly authorized source audit. Require the historical 40-token stage 1 and 16-token stage 2 contract, two-stage order including stage-1 parse-invalid behavior, and an explicit decision for the predeclared termination rule. Do not substitute P0 act or a fake parser for that production operator.
2. Explicitly choose and bind whether recovery runs on native Qwen3-8B or a particular adapter. The completed action run used `OfflineP0` with an attached PEFT adapter and a P0 64-token generation (`direct_worker.py:166-180,208-215`), not native H4 recovery. The H4 history is no evidence the P0 adapter is recovery-compatible. A shared base snapshot alone does not establish equivalent identity or behavior. Pin adapter presence/absence, version, load path and expected placement; validate this at runtime and do not attach it implicitly.
3. Replace the one-shot generation guard with a stage-bound guard enforcing at most 2 physical `model.generate` calls in order, stage 1 <=40 new tokens and stage 2 <=16, one input tensor row <=4096 each, no hidden beam/return multiplication, and no third call on any failure. Consume the permission before call entry. Preserve separate operation starts, actual arguments and bounded raw outputs/IDs, returns/unknown and token counts per stage. Inspect the *actual* final tensors at `model.generate` rather than relying solely on prompt metadata or a synthetic precheck. Invalid stage-1 parse by itself must not skip stage 2 if the bound historical operator says otherwise; any physical exception, resource stop, missing evidence, unauthorized output or invalid final action stops and never retries. Exact parsing and its historical empty-diagnosis behavior remain unchanged.
4. Instrument real physical boundaries, not just the outer `act`: Qwen `_load` contains tokenizer `from_pretrained`, model `from_pretrained`, device move and eval (`src/models/qwen.py:200-234`), while the old `backend_load` wraps the whole bundle (`direct_worker.py:166-178`). Either wrap actual internal entry points with stage-specific fsync START/RETURN/UNKNOWN, or label each internal count UNKNOWN; outer `_load` return cannot prove each physical operation independently. Adapt guards without altering production decision logic, and check that subsequent cached `_load` calls cannot evade or duplicate accounting. Similarly old `TokenizerCapture` logs only after render/encode/decode returns (`capture.py:2-25`): add before-call persistence and failures/unknown for each *actual* render, encode, decode, and any internal tokenization. Do not count post-hoc CPU re-tokenization as the model worker's calls; explicitly budget separate audit operations. Guard `.generate` is the physical call boundary, but CUDA asynchronous completion/tails remain UNKNOWN without an appropriately scoped synchronisation/measurement contract.
5. Adapt `OneActionCore`, owner `check_guard` (`owner.py:49-62`), lifecycle checks, result schemas, wire semantic audit and CPU auditing: all were built for a single P0 output and old 64 cap (`wire_audit.py:35-46`, `cpu_ops_ledger.py:12`). Cross-check both actual stages, production parser results and the same environment-owned action mapping. Before optional step, require a final action uniquely maps to the current case's command and recorded stage provenance; no step on missing/ambiguous/invalid result or exception. Keep max 1 construct, 1 load, 1 reset, optional 1 step and close, with physical operation start/return/UNKNOWN and raw bounded returned evidence preserved *before* semantic validation. A close needed for cleanup must itself be logged, and cleanup write failures remain UNKNOWN.
6. Construct a new fixed identity, fresh output and claim, pre-GO work-start journal, exact byte bindings and disabled implementation first. Test with injected fake boundaries, crash/write/fsync/interrupt faults, two-stage limits and overflow, valid/invalid stages, ambiguous action, no retry, owner death, sampled resource failures and independently reviewed complete cost accounting. Independent exact-byte review and fresh admission are needed before any decision to enable; fake tests do not demonstrate real integration or readiness.

## Budget and interpretation

A proposed ceiling is one model bundle, at most two `model.generate` calls with distinct 40/16 output caps and 4096 input cap each, one environment construct/load/reset, at most one step and a close, plus tokenizer and separately scoped CPU auditing. This is a new proposed budget, not the old one-call/64-token budget, nor authorization to execute. Specify model-load internals, tokenizer counts, output evidence, resource sampling, all setup/cleanup costs and terminal UNKNOWN before launch. Prior reported 12,113 generations / 15,317 reset-inclusive operations are a named selected subtotal, not total project cost; track separately and retain unobserved costs UNKNOWN (`ROOT_EXECUTION_RECORD.md`, `COST_SCOPE_CLARIFICATION.md`).

No guarantee is made for whole-tree limits, escaped descendants, kernel/device work after stop, resource reservation, continuous monitoring, independent provenance, or full native operation accounting. A future successful engineering probe would not establish scientific effectiveness, independent task lineage, SFT-P0/H4 comparability or model improvement.
