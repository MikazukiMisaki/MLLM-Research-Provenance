# State-selection CPU prototype — HOLD / unverified claims

Standalone program for the v5 design's paired selection rules. It is not a production data converter, source identity verifier, model/training launcher, or evidence of a usable dataset. It was exercised only with entirely fictional trajectories, mappings, token IDs, success claims, paths and parent lineage; no real task/model/environment was accessed. The accepted `SI_STATE_SELECTION_DEMO_V1` JSON schema is a deliberately provisional *adapter format*, not an observed production trace or validated SFT trainer input.

The caller provides a manifest file under its input root and its exact SHA-256. Every consumed file is explicitly listed by relative path and byte hash in that manifest; parent/episode ordering is exactly the manifest ordering and each of exactly 16 predeclared parents supplies exactly one episode. There is no replacement. Claimed train and evaluation parent IDs and lineage tags must be disjoint. Exactly 16 evaluation parents are required. For each successful claimed episode the code reconstructs history from the recorded action sequence, then finds the first ordered pair whose target history ends with exact `look, examine X, look, examine X` and whose control does not, using the same episode, action ID, command, full target token IDs and full per-token loss mask. In this provisional representation, the full trainer sequence must be exactly prompt IDs followed by target IDs with corresponding mask, at most 4096 total and 16 target IDs. This representation intentionally fails closed for other trainer formats; it has not been established as the real trainer transformation. Source identity, execution identity and lineage authenticity are always UNKNOWN; claims are never promoted by this program into verified provenance.

Each accepted row preserves all four per-decision file references plus its episode and terminal references; their individual expected hashes live in the separately pinned manifest. Both result JSONLs are written only after the complete selection passes. `status.json` uses `SELECTED_UNVERIFIED_CLAIMS` or `REJECTED` and a reason; errors can leave partial output if output I/O fails, so consumers must require successful status and independently verify all files before considering anything. Each output directory must be new; no source file or old output is overwritten. No partial cohort, repair, resampling, replacement or retry occurs.

**Limits requiring independent work:** hashes only bind bytes to a caller-supplied manifest, not their truth, original location, actual product or physical execution. In particular the provisional terminal file contains only claimed boolean completion/win, not independently authenticated binding to that episode; action text and label token IDs are not independently verified as one original generated response. The program also does not authenticate lineage, the first-episode/source roster, tokenizer/trainer transformation, action mapping origin, model context, or source execution. It does not reconstruct or validate original native terminal semantics, acceptance/precision thresholds, loss computation or GPU costs. Same-UID race resistance and atomic durable outputs have not been proved. The current output is a selection ledger of references, not a ready-to-train JSONL; it must not be treated as research evidence without a separately reviewed adapter, source evidence and full runtime integration.
