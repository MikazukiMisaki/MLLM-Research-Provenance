## Loader and host-memory implications

The inspected production Qwen loader passes `device_map='auto'` only for `device='auto'`; automatic dispatch may place weights on GPU, CPU or disk depending on the installed library and available resources. It does not by itself establish a single-GPU placement or rule out offload. The policy then sends input tensors to `model.device`, which is not proof that every parameter or runtime allocation is on the same device. Review the actual loaded device map, parameters/buffers, adapter placement and relevant dispatch/offload hooks before any single-GPU/no-offload claim; even those observations are not a complete native allocation trace.

For `device='cuda'`, the inspected loader calls `from_pretrained` without that automatic map, then invokes `.to('cuda')`; this creates a host-side loading phase and a subsequent transfer. It can require substantial host RAM and transient copy/serialization overhead, but exact peak and loading strategy cannot be inferred from source or disk size. The PEFT adapter is attached afterward by the production policy. A bounded design must inspect host/cgroup capacity and enforce/monitor appropriate process-tree and elapsed/resource limits without harming other users; a GPU-free check alone is insufficient.

## Minimum conditions for a future bounded engineering run

- Independently freeze and verify the exact source, interpreter/runtime, local model/tokenizer/adapter and self-authored task identities; resolve the previous aggregate model-hash verification failure rather than describing it as a full PASS. No protected historical task access is needed.
- Review an actual single-use worker/supervisor and its exact argv/environment and output identity; bound construct/load/reset, tokenizer/model/adapter load, one model generation and at most one step, with no automatic retries. Account started, completed, failed and unknown operations separately; record internal environment conversions and other unobserved cost as unknown rather than zero.
- Choose and enforce device placement and a defensible provisional admission/stop policy. Use a reserved-aware query and recorded actual `free` value; recheck immediately before allocation and monitor shared-device and owned-process conditions. Distinguish device-wide telemetry, process-visible information and unknown PID ownership. No floor can create a hardware reservation.
- Check the actual tensor and token IDs delivered to the model and enforce the reviewed input/output caps before generation. Previously observed list-mode prompt IDs do not establish future tensor identity. Verify the actual selected public action has unique environment grounding before any step and preserve ambiguous/invalid outputs without retries.
- Retain original events, process exits, partial artifacts, exact source hashes and external anchors. On load failure, OOM, timeout, changed inputs, lost monitoring, unknown process state or invalid evidence, stop the owned work, preserve unknown tails and do not classify the attempt as free.

Do not state that 24,576 MiB guarantees fit, that the current point-in-time sample guarantees future availability, that auto placement uses only the A40, that CPU/GPU peaks or allocated device-hours are known from these calculations, or that one model action is evidence of self-improvement. A genuine small engineering load would require a separately reviewed exact candidate; no such load was performed here.
