# Independent review: guardian diagnostic candidate

Decision: **NOT APPROVED FOR LIVE USE**. Candidate `guardian_candidate.py` SHA256 `fc7c1cc2768ceb20eca2a4f18bd709c3a15309d650b63cfa10f5eecdab26202d`; comparison baseline is the formerly used enabled guardian SHA256 `77cb06dc267234d69d9f0a1d8a2b7d3e9e62447180c8c0e3ac64c2fedb86850b`. The candidate itself keeps real entry disabled. This review used only isolated self-created subprocesses and did not open the completed scientific run, launch training, initialize CUDA, load a model or create an environment.

The final status predicate continues to require no observation errors, no failure or timeout and a direct return code of zero. All 25 former assignments of `observed_unknown = True` are replaced by a helper that sets it before recording the diagnostic. Seven candidate synthetic tests independently passed; log SHA256 `d7b8f157c4be1f474353830b0a6b13785be505e430566fd1ef4d27e380d9eae3`. The tests cover selected fault branches, not all possible failures or real workloads. Existing guardian uncertainty about unobserved descendants and costs remains.

**Major — new synchronous diagnostic write can delay stop/cleanup.** The new helper calls `journal.record` and its fsync synchronously from process discovery, signal, resource and cleanup paths, before control returns to deadline and cleanup code. A blocked write can delay signaling a still-running child without a separate independent watchdog; as many as 256 events can invoke that path. The independent fake `slow_diagnostic_probe.py` injected one 0.7-second diagnostic write delay against a 0.2-second fixture budget. Wall time was 0.914 seconds, with real fake-child return code -15 and final status `STOP_FAILED_OR_UNKNOWN`. Probe SHA256 `b5323d15924594bd1ee279a59737fcd93edb6564c459f393267266f84fb5bcf2`; raw output SHA256 `a44e9a7402327f35d5f59833bab6502fdd4c8e368ba249dc49081f02af3f7a25`. The preexisting guardian already had blocking I/O and non-hard timing limits; this adds synchronous I/O to additional fault and cleanup paths. Before use, remove synchronous diagnostic persistence from these time-sensitive paths or independently demonstrate an acceptable bounded design, then re-review its exact bytes.

Diagnostic rows contain constant stage/reason values, exception class, monotonic time and PID/start tick only for identities already in the guardian's owned records or the guardian itself. Unverified candidate PIDs are omitted. Those identity fields are still private process metadata and should not be published without explicit review. The design does not record exception messages, environment values or command arguments in these new rows. There is no proof of all possible dynamic exception-class names. If journal writes fail, the in-memory write-failure flag is set and UNKNOWN retained, but a partial write can invalidate the chain; a crash or final receipt write failure can lose diagnostic details or the receipt entirely. The 256-row cap can omit subsequent details and flags truncation only if a receipt survives. Review coverage does not establish kernel-level containment, durable persistence across crash, or a complete account of unobserved processes.

This finding is prospective software-control evidence only. The completed real run's `observation_errors=true` and resulting UNKNOWN remain unchanged. No result, launch permission, retry or scientific success is implied.
