# Effect IPC candidate v2: strict sequence types and parent-directory sync

This isolated revision fixes two independently reproduced v1 issues without changing any frozen source or old evidence. It is a fictional CPU protocol candidate, not an authenticated production owner or execution permission.

- `receipt_check` now requires actual Python `int` (not bool or float) for every child JSONL row `seq` and present `owner_seq`, and for the matching request sequence. It validates the exact current `SI_STAGE_WORKER_V1` event envelope keys and strict basic types, plus exact started / returned / unknown payloads for known operations. Unrelated non-effect journal events remain allowed, so started and returned need not be adjacent. Full JSONL line including newline remains the receipt hash; the original child IPC source is unchanged. Parent wire messages enforce exact field sets, integer sequence and string operation/receipt/status. These checks do not authenticate the child or prove physical work.
- On parent ledger creation, the file is fsynced and its containing directory opened and fsynced before any child starts. An exception closes the file, raises `LedgerCreationUnknown`, and makes a best-effort `creation_unknown` marker; it does not start a child or assert the marker persisted. File or directory sync errors can make even this marker nondurable.

The pinned Python/PyTorch CPU test process returned exit 0 (`test-output.log`, `test-output.exit`): four cases comprising the original fictional 163-effect normal and first-step interruption regressions, explicit bool/float seq and owner_seq rejection with correctly rehashed fixtures, and a simulated directory-fsync failure verifying rejection before child creation. No model/weights/task/ALFWorld/CUDA or real experiment was used.

Durability remains limited: syncing the ledger's containing directory does not prove persistence of the separately created root directory's entry in its own parent; no process-kill, power-loss, storage-controller or filesystem semantics were tested. Runtime file reads still lack comprehensive production-grade file identity/TOCTOU/cap controls. Parent/child authentication, one-use authorization across directories, hidden descendants, process ownership, GPU/PEFT, physical cost, complete budgets and checkpoint validity remain unproven. `dispatch_real` remains HOLD. See `v1-to-v2.diff` for exact changes and `prior-source-hashes.json` for unchanged prior references.
