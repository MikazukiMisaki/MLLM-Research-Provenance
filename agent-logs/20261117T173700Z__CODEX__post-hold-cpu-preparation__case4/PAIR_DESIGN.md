## Proposed lifecycle: one materialization per pair

1. A single supervisor owns a fixed four-case roster, fixed arm order and one durable batch budget. It creates a fresh batch directory exclusively, a pair directory exclusively, and per-arm output directories exclusively. It holds the shared GPU coordination lock for the run and treats unrecognized compute PIDs or unsatisfied resource conditions as stop, never as belonging to its worker by PID resemblance. The batch/pair clock starts according to the frozen plan; do not silently restart a deadline when a process changes.
2. Before touching task inputs for pair i, supervisor's global effect owner durably records and fsyncs `materialize RESERVED` with batch and pair identity. Allow at most four reservations batch-wide and one per pair; an in-flight or failed reservation still consumes the limit. A separate CPU-only setup child, under supervisor's ownership and effect channel, invokes the *existing real* `materialize(pair_dir, inputs, ..., family="two")` exactly once. No model, environment or GPU is needed for setup. Setup child verifies the resulting bytes/structure with actual `verify_materialized(..., "pre")`, emits returned path/hashes and terminates; owner durably marks returned after validating receipt. Any unknown completion, failure, child leak, timeout, or unexpected file stops the study; no rematerialization or retry.
3. Supervisor validates all returned paths lie under the one pair root, checks regular-file/no-symlink/no-hardlink identity and canonical path set, and records hash-bound pair receipt for the exact source game/config/routing, generated game/routing/config bytes and directory inventory, code, case ID and seed. Each of two independent arm child configurations embeds this same immutable receipt SHA, identical absolute three paths and input hashes, plus unique arm identity, product hash, output path and shared-budget capability. Their writable outputs are separate and outside the pair input subtree. Do not patch production config, copy files, choose a different route, or share an environment instance between arms.
4. Immediately before first arm, at end of first arm after its environment closes, before second arm, and at end of second arm, perform the *real* source/materialized verification, plus deterministic inventory and receipt rechecks; record each result. The first worker constructs/initializes/resets its own ALFWorld instance with fixed seed, records public initial state and hash, runs its original product once, closes and exits. Supervisor records any known native outcome before checking cleanup. If first arm is incomplete, input integrity unknown, or descendants remain, stop. It binds the exact saved initial public state and SHA into the second worker's config. Second child verifies its own reset equals the saved public state before loading its own product or taking its first action; mismatch stops without a retry. Equal public state and bytes do not prove equal hidden state.
5. Between children, wait for first exit, owned-child/subreaper cleanup and valid budget completion; do not kill unrelated processes or infer ownership from numerical PID mapping. Recheck GPU admission before the next model load. Each child uses only its own production model+environment, writable output and lifecycle, but reads the same pair-owned task files. Preserve arm and pair outcomes and evidence on error. After second child exits, verify task integrity and cleanup; retain the pair input and logs until provenance archival/hash verification. Do not delete failed/unknown data.
6. Only after complete pair processing advance to the next separately materialized pair, in frozen order. Finalize only when all four cases and all eight eligible outcomes are present; an incomplete roster is UNKNOWN, never success/failure imputation. Use native `done && won` evidence; production policy/invalid-format classification stays as defined in the reviewed plan. Preserve all incomplete reservations and worker result receipts.

## Budget, crash semantics and concurrent isolation

- One authoritative parent budget counter covers setup and both arms across *all* cases: materialize <=4 total and <=1 per pair; model loads/resets/environment constructions/initializations <=8 each; generations and steps <=400 each; token and time caps as above. Per-arm child counters additionally cap one load/reset/construction/initialization and 50 generations/steps. Setup has zero model or environment allowances. Children have no separate ability to grant/replenish budget and no automatic retry.
- Reserve before external side effects; durably record operation id, pair, arm (or setup), kind, owner decision and cap snapshot before ACK, then append returned/failed/unknown with correlated worker receipts. ACK loss, parent/child death, unexplained timeout, unfinished effect, counter inconsistency or write/fsync failure means stop with reservation counted and result unknown. Persist parent log rather than recomputing limits from only completed children. If owner dies, do not start a successor in the same authorization; reconstruct costs offline from reservation, return and OS receipts without treating unreturned operations as free.
- Pair tree should be read-only to workers using an actually enforceable OS isolation mechanism if available and validated; mode bits alone do not protect against a same-UID process that can chmod. Where such enforcement is unavailable, record that limitation and use pre/between/post byte and inventory checks, separate output directories and single-owner execution; hashes detect observed changes but cannot prove no transient mutation. No claim of strong filesystem isolation based on checksums alone. Verify that the real environment needs no writes within the input tree before making immutability a hard requirement; if it does, resolve and review rather than silently copying or changing behavior.
- Parent must keep open-file/symlink/path substitution and TOCTOU risks explicit; regular-file checks, exclusive creation, canonical containment, source checks before/after and single owner reduce but do not eliminate mutable filesystem races. Never call an existing-byte copy 'zero cost' unless the review explicitly defines and accounts for it as distinct from the frozen materialization budget. The proposed design performs no per-arm task copy.
